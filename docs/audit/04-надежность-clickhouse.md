# Надёжность загрузки в ClickHouse

Этот раздел отвечает на второй симптом заказчика: **«данные сначала попадают в кэш, потом в базу; кэш быстро забивался и переставал принимать данные»**. Разберём, что здесь на самом деле за «кэш», и почему приём вставок вставал.

Серьёзность: 🔴 Критично · 🟠 Высокий · 🟡 Средний · ⚪ Низкий

---

## Что за «кэш» на самом деле

В коде включён режим асинхронной вставки:
```
INSERT INTO ... SETTINGS async_insert = 1, wait_for_async_insert = 1, input_format_parallel_parsing = 1 FORMAT JSONEachRow   // строка 408
```

`async_insert = 1` — это и есть «кэш»: ClickHouse не пишет строки сразу в таблицу, а складывает их в **буфер асинхронных вставок** в памяти сервера. Буфер сбрасывается на диск (в куски таблицы), когда накопит достаточно данных (`async_insert_max_data_size`) или по таймауту (`async_insert_busy_timeout_ms`). Это оправдано, когда много клиентов шлют **мелкие** вставки по одной строке. Здесь же клиент один и шлёт **пачки по 5000 строк** — то есть ровно тот случай, когда async-режим не нужен и вреден.

Но само по себе переполнение async-буфера — не главная беда. Главная — **мутации от удалений**, которые ломают фоновые слияния и приводят к состоянию «слишком много кусков», при котором ClickHouse **отклоняет вставки** (ошибка `TOO_MANY_PARTS`). Именно это внешне выглядит как «кэш забился и перестал принимать данные». Разберём по порядку.

---

## 🔴 CH-01. Шторм мутаций `ALTER TABLE … DELETE` — главный убийца загрузки

**Где:** `КХ_УдалитьДанные` (строки 380–382):
```
ALTER TABLE <таблица> DELETE WHERE <поле> IN (...) SETTINGS mutations_sync = 2, max_execution_time = 0
```
Вызывается **перед каждой вставкой**: на каждую пачку каждой таблицы, плюс на каждую табличную часть каждой пачки (строки 191, 222, 242, 283, 310).

**Почему это разрушительно для ClickHouse.**
- `ALTER TABLE … DELETE` в ClickHouse — это **мутация**, а не обычное удаление. Она асинхронно **переписывает целые куски данных** (data parts), исключая удаляемые строки. Мутация тяжёлая: она затрагивает куски целиком, даже если удаляется одна строка.
- Каждая мутация создаёт новые куски и порождает работу фоновому слиянию (merge). При суточном запуске по многим таблицам, с пачками и табличными частями, число мутаций в день — **десятки и сотни**.
- Пока идут мутации и слияния, растёт число **активных кусков**. Когда их в партиции становится больше `parts_to_throw_insert` (по умолчанию 300), ClickHouse начинает **отклонять любые вставки** с ошибкой `TOO_MANY_PARTS`. Приём данных встаёт — ровно наблюдаемый симптом.
- `mutations_sync = 2` заставляет клиента **ждать завершения мутации на всех репликах**, а `max_execution_time = 0` снимает ограничение по времени — то есть запрос удаления может ждать **бесконечно** (см. CH-03). Пока копятся невыполненные мутации, каждое новое удаление ждёт всё дольше.

**Вывод.** Схема «удалить мутацией, потом вставить», выполняемая десятки раз за запуск, — это антипаттерн ClickHouse. ClickHouse не рассчитан на частые точечные удаления; мутации задуманы как редкие административные операции. Именно этот механизм, а не переполнение памяти буфера, ставит загрузку.

**Как правильно (принципиально).** Отказаться от удалений при регулярной загрузке. Целевой подход — **вставка новой версии + фоновое схлопывание старых** через `ReplacingMergeTree` (движок сам оставляет последнюю версию по ключу), либо загрузка партициями с атомарной заменой партиции (`REPLACE PARTITION`), где это ложится на модель данных. Тогда регулярная работа — это только `INSERT`, без единой мутации. Подробно — в [целевой архитектуре](06-целевая-архитектура-и-план.md).

## 🟠 CH-02. `async_insert = 1` не нужен при пачках и создаёт лишний слой ненадёжности

**Где:** строка 408.

**Суть.**
- Клиент шлёт крупные пачки (5000 строк) от одного источника. Для этого сценария прямой синхронный `INSERT` эффективнее и надёжнее: данные сразу становятся куском, судьба вставки однозначна по HTTP-ответу.
- `async_insert = 1` добавляет промежуточный буфер в памяти сервера: несколько пачек «зависают» в нём до сброса. При большом потоке буфер растёт; его переполнение и частые сбросы мелкими кусками усугубляют проблему множества кусков (см. CH-01).
- `wait_for_async_insert = 1` частично компенсирует (клиент ждёт подтверждения записи буфера), но это не запись в таблицу, а именно приём в буфер — семантика доставки менее очевидна, чем при синхронной вставке.
- `input_format_parallel_parsing = 1` для JSONEachRow полезен на больших телах, но в связке с async-буфером выгоды почти не даёт.

**Как правильно.** Для пачечной загрузки использовать **синхронную** вставку (`async_insert = 0`) — детерминированный результат на каждую пачку. async_insert оставить только если перейти на модель «много мелких частых вставок», что здесь не нужно.

## 🟠 CH-03. `mutations_sync = 2` + `max_execution_time = 0` + отсутствие таймаута HTTP = потенциально вечное зависание

**Где:** `КХ_УдалитьДанные` (строка 382) и `ОтправитьHTTP` (строки 721–734) — таймаут соединения не задан (`Новый HTTPСоединение(Хост, Порт, , , , , Неопределено)` — параметр таймаута опущен).

**Суть.** Три фактора складываются:
1. `max_execution_time = 0` — ClickHouse не ограничивает время выполнения мутации.
2. `mutations_sync = 2` — клиент ждёт применения мутации на всех репликах.
3. У HTTP-соединения 1С не задан таймаут — 1С ждёт ответа неопределённо долго.

Если мутации накопились (см. CH-01) или кластер под нагрузкой, удаление может ждать **очень долго или бесконечно**, удерживая серверный вызов 1С и блокируя весь дальнейший конвейер. Регламентное задание «висит», следующее по расписанию может наложиться (см. A-02).

**Как правильно.** Задать разумный таймаут HTTP-соединения в 1С; на стороне запроса — ограничить `max_execution_time`; при переходе на схему без мутаций проблема исчезает вместе с удалениями.

## 🟠 CH-04. DELETE со списком из 5000 ссылок может превысить `max_query_size`

**Где:** `КХ_УдалитьДанные` (строки 363–382): список ссылок вставляется инлайном в текст запроса `IN ('...','...', … )`.

**Суть.** Ключ здесь — **навигационная ссылка** (длинная строка, см. K-09/CH-10), по 5000 штук в одном `IN`. Текст запроса легко достигает сотен килобайт — мегабайтов. У ClickHouse есть лимит на размер запроса `max_query_size` (по умолчанию 256 КБ). При превышении удаление вернёт ошибку → по логике кода вставка не выполнится (удаление != 200), пачка помечается ошибкой удаления и пропускается (строки 198–200, 259–264, 326–331) → данные не обновятся. Чем крупнее ключи, тем раньше упрёмся в лимит.

**Как правильно.** Не передавать большие списки в тексте запроса. Использовать UUID (короткие ключи) и/или передавать список ключей через внешние данные/временную таблицу; в целевой схеме удаления нет вовсе.

## 🟠 CH-05. Сетевые исключения не перехватываются — одно падение роняет всё задание

**Где:** `ОтправитьHTTP` (строка 731) `Соединение.ОтправитьДляОбработки(Запрос)` не обёрнут в `Попытка`; вызовы `КХ_УдалитьДанные`/`КХ_ОтправитьДанные` в основном цикле тоже без `Попытка`.

**Суть.** `ОтправитьДляОбработки` выбрасывает исключение при недоступности хоста, обрыве соединения, таймауте, ошибке TLS. Исключение нигде не ловится → падает вся процедура `КХ_Загрузить_из_ОС`. Последствия:
- один сетевой сбой на любой пачке любой таблицы **прекращает выгрузку всех оставшихся** объектов;
- уже выполненные удаления не компенсируются (усугубляет K-02 — дыры в данных);
- задание завершается аварийно, накопленная статистика ошибок не выводится (код до итоговых `Сообщить` не доходит).

Это прямое нарушение требования «надёжно»: любой сетевой чих обнуляет весь суточный прогон.

**Как правильно.** Каждую сетевую операцию — в `Попытка/Исключение` с логированием; сбой одной пачки/таблицы не должен прекращать обработку остальных; добавить ретраи с паузами (экспоненциальная задержка) и, при исчерпании, — пометку «повторить в следующий запуск», а не потерю. См. [целевую архитектуру](06-целевая-архитектура-и-план.md).

## 🟡 CH-06. Дрейф схемы: новый реквизит в 1С молча ломает все вставки таблицы

**Где:** `ВЫБРАТЬ *` (строки 552, 651) + `FORMAT JSONEachRow` со `structure` из данных.

**Суть.** Состав полей JSON определяется реквизитами объекта на момент выгрузки (`ВЫБРАТЬ *`). Если в конфигурацию 1С добавят/переименуют реквизит, в JSON появится новое поле (после транслитерации). Дальше зависит от настроек ClickHouse:
- при строгой проверке (`input_format_skip_unknown_fields = 0`) вставка с неизвестным полем **упадёт** — и так для **всей** таблицы, пока не поправят DDL;
- при `= 1` поле молча отбрасывается — данные тихо теряются.

Схема ClickHouse (DDL) в репозитории отсутствует (см. A-08), поэтому соответствие «реквизит 1С ↔ колонка CH» нигде не зафиксировано и не проверяется. Любое изменение метаданных — потенциальная тихая поломка.

**Как правильно.** Явный список выгружаемых полей (см. P-05); версионирование схемы; согласованные миграции DDL ClickHouse вместе с изменениями конфигурации; мониторинг ошибок вставки по таблицам.

## 🟡 CH-07. NULL в не-Nullable колонки: тихие дефолты, контракт типов не зафиксирован

**Где:** массовое превращение значений в `Неопределено` (см. K-07) + `КХ_СформироватьJSON` (строки 705–715).

**Суть.** В JSONEachRow `null` для **не**-Nullable колонки ClickHouse подставит дефолт типа (0, пустая строка), а не ошибку — при `input_format_null_as_default = 1` (по умолчанию включено). Это накладывается на K-07: `0`/`Ложь`/`""`, ставшие `null`, в ClickHouse превратятся обратно в `0`/`""` — иногда «случайно правильно», иногда нет (для дат, перечислений, ссылок дефолт бессмысленен). Итог — данные молча искажаются, ошибок не видно.

Кроме того, `КХ_СформироватьJSON` пишет значения без явного контроля целевого типа: число, булево, строка сериализуются как есть, дата — как строка. Соответствие типов колонкам ClickHouse нигде не проверяется.

**Как правильно.** Зафиксировать контракт типов (Nullable там, где значение действительно опционально; иначе — корректное значение, а не `null`); не терять `0`/`Ложь`; согласовать форматы дат (см. CH-09) с типами колонок.

## ⚪ CH-08. Пустые INSERT для пустых табличных частей

**Где:** обработка ТЧ (строки 244–246, 312–314): для каждой ТЧ выполняется DELETE и INSERT, даже если данных ТЧ в пачке нет.

**Суть.** Если у документов пачки данная табличная часть пуста, `КХ_ПолучитьДанныеТЧИзБазы` вернёт пустой массив, `КХ_СформироватьJSON` — пустую строку, но `КХ_ОтправитьДанные` всё равно отправит INSERT с пустым телом (и перед этим — мутацию DELETE). Это лишние мутации и запросы «ни за чем», усугубляющие CH-01.

**Как правильно.** Пропускать удаление/вставку, если для пачки нет данных ТЧ.

## ⚪ CH-09. Смешанные форматы дат, таймзоны не оговорены

**Где:** `КХ_ПреобразоватьЗначение` (строки 882–895): дата сериализуется то как `yyyy-MM-dd`, то как `yyyy-MM-dd HH:mm:ss`, «нулевая» дата → `null`; плюс эвристика обрезки строк под дату (K-13).

**Суть.**
- В одну и ту же колонку ClickHouse (Date/DateTime) прилетают значения то с временем, то без — парсинг зависит от типа колонки; для `DateTime` значение `yyyy-MM-dd` будет интерпретировано как полночь, что может быть неверно.
- Таймзона нигде не задаётся. `DateTime` в ClickHouse хранит момент в UTC и интерпретирует вход в таймзоне колонки/сервера; 1С отдаёт локальное время сеанса. Без явной таймзоны возможен сдвиг дат/времени.
- «Нулевая» дата 1С (0001-01-01) корректно превращается в `null`, но пустая дата в не-Nullable DateTime-колонке даст дефолт `1970-01-01` (см. CH-07).

**Как правильно.** Единый формат под тип колонки; явно определить таймзону (хранить в UTC или фиксированной TZ, согласованной с колонкой); документировать соглашение.

## ⚪ CH-10. Длинные навигационные ссылки как ключи вместо UUID

**Где:** поле `ssylka` — навигационная ссылка (`ПолучитьНавигационнуюСсылку`, строка 870), по нему идут и удаление, и идемпотентность, и обратный парсинг (K-09).

**Суть.** Навигационная ссылка — длинная строка вида `e1cib/data/Справочник.…?ref=…`. Как ключ она:
- раздувает размер запросов DELETE (см. CH-04) и объём хранения/индексов в ClickHouse;
- нестабильна (зависит от способа получения, ломается на предопределённых — K-09);
- плохо индексируется относительно короткого фиксированного UUID.

**Как правильно.** Ключом сделать `UUID` объекта (`Строка(Ссылка.УникальныйИдентификатор())`) — 36 символов, стабильно, компактно; представление хранить отдельным необязательным полем.

## Итог: почему «кэш забивался» и как это убрать

Наблюдаемое «кэш забился и перестал принимать данные» — это сумма двух причин:
1. **Главная — CH-01:** десятки/сотни мутаций `ALTER … DELETE` в день ломают фоновые слияния, число активных кусков растёт, ClickHouse отклоняет вставки (`TOO_MANY_PARTS`).
2. **Сопутствующая — CH-02:** async-буфер вставок (тот самый «кэш») копит данные в памяти и сбрасывается мелкими кусками, что добавляет кусков и усугубляет (1).

**Оба симптома устраняются одним архитектурным решением:** убрать удаления и async-режим из регулярной загрузки, перейти на `INSERT` в `ReplacingMergeTree` (или замену партиций) с синхронной вставкой. Тогда регулярная работа — это только вставки крупными кусками, без мутаций и без разбухания буфера.

| ID | Ур. | Проблема | Ключевое исправление |
|---|---|---|---|
| CH-01 | 🔴 | Шторм мутаций DELETE | Отказ от удалений: ReplacingMergeTree / REPLACE PARTITION |
| CH-02 | 🟠 | Ненужный async_insert («кэш») | Синхронная вставка пачками |
| CH-03 | 🟠 | Бесконечное ожидание мутации | Таймауты HTTP и запроса; нет мутаций |
| CH-04 | 🟠 | Огромный DELETE `IN (...)` | UUID-ключи; нет инлайн-списков |
| CH-05 | 🟠 | Непойманные сетевые исключения | `Попытка` + ретраи вокруг каждой операции |
| CH-06 | 🟡 | Дрейф схемы ломает вставки | Явные поля, миграции DDL, мониторинг |
| CH-07 | 🟡 | NULL → тихие дефолты | Контракт типов, не терять 0/Ложь |
| CH-08 | ⚪ | Пустые INSERT/DELETE для пустых ТЧ | Пропускать пустые |
| CH-09 | ⚪ | Смешанные даты/таймзоны | Единый формат и TZ |
| CH-10 | ⚪ | Длинные ссылки как ключи | UUID |

Полное описание целевой схемы — в [06-целевая-архитектура-и-план.md](06-целевая-архитектура-и-план.md).
