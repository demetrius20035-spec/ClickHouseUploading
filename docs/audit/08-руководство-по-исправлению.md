## 1. Переход с «удаление + запись» на ReplacingMergeTree и атомарность «шапка + табличные части»

### 1.1. Почему это главное исправление

Сейчас каждая пачка — это `ALTER TABLE … DELETE` (строки 377–379) и затем `INSERT`. `ALTER DELETE` — **мутация**: ClickHouse физически перезаписывает куски таблицы. Десятки таблиц × пачки × ТЧ = сотни мутаций за прогон. Очередь слияний забивается, число активных кусков растёт, и при `parts_to_throw_insert` (по умолчанию 300) ClickHouse начинает **отклонять вставки** — это и есть наблюдавшееся у вас «кэш забился и перестал принимать данные» (CH-01/CH-02 из [04-надежность-clickhouse.md](04-надежность-clickhouse.md)).

Целевая схема убирает мутации полностью: **только INSERT**. Старые версии строк не удаляются в момент выгрузки — они вытесняются логически, по номеру версии.

### 1.2. Схема таблиц

Каждая таблица получает два служебных поля:

- `_version UInt64` — номер версии строки. **Одна версия на весь прогон выгрузки**, вычисляется один раз в начале `КХ_Загрузить_из_ОС`;
- `_is_deleted UInt8` — мягкое удаление (0 — жива, 1 — удалена в 1С). На первом этапе можно не использовать (всегда 0), поле нужно заложить сразу, чтобы не менять схему второй раз.

DDL (имена колонок — примерные, перенесите ваши фактические):

```sql
-- Шапка документа: одна строка на ссылку
CREATE TABLE mega.dokument_postuplenie_na_raschetnyy_schet_v2
(
    ssylka      String,          -- навигационная ссылка или UUID
    data        DateTime,
    nomer       String,
    -- ... остальные реквизиты ...
    _version    UInt64,
    _is_deleted UInt8 DEFAULT 0
)
ENGINE = ReplacingMergeTree(_version)
ORDER BY ssylka;

-- Табличная часть: строка на (ссылка, номер строки)
CREATE TABLE mega.dokument_postuplenie_na_raschetnyy_schet_tovary_v2
(
    ssylka        String,
    nomer_stroki  UInt32,
    -- ... реквизиты ТЧ ...
    _version      UInt64,
    _is_deleted   UInt8 DEFAULT 0
)
ENGINE = ReplacingMergeTree(_version)
ORDER BY (ssylka, nomer_stroki);

-- Регистр накопления: строка на (регистратор, номер строки)
CREATE TABLE mega.registr_nakopleniya_prodazhi_v2
(
    registrator   String,
    period        DateTime,
    nomer_stroki  UInt32,
    vid_dvizheniya UInt8,
    -- ... измерения и ресурсы ...
    _version      UInt64,
    _is_deleted   UInt8 DEFAULT 0
)
ENGINE = ReplacingMergeTree(_version)
ORDER BY (registrator, nomer_stroki)
PARTITION BY toYYYYMM(period);
```

Важные детали:

- **Ключ сортировки = естественный ключ строки**, не периода. Для регистра — `(registrator, nomer_stroki)`: тогда перепроведённая строка с изменившимся `period` **заменяет** старую, а не живёт рядом с ней. `period` в ключ не включайте.
- `ReplacingMergeTree(_version)`: при слиянии из строк с одинаковым ключом сортировки остаётся строка с максимальной `_version`. Повторная вставка той же пачки с той же версией безвредна — дубли схлопываются. Это даёт **идемпотентные ретраи**.
- Вариант `ReplacingMergeTree(_version, _is_deleted)` (движок сам выкидывает удалённые при `FINAL`) требует ClickHouse ≥ 23.2. Если версия сервера ниже — используйте `ReplacingMergeTree(_version)` и фильтруйте `_is_deleted = 0` во view (ниже).
- В `РегистрНакопления` в 1С нет поля «номер строки» в выборке `ВЫБРАТЬ *`? Есть — `НомерСтроки` присутствует в основной таблице регистра и попадает в `ВЫБРАТЬ *` (после транслитерации — `nomer_stroki`). Проверьте, что колонка реально доезжает до CH.

### 1.3. Ловушка FINAL и как читать данные (поправка Ф-03)

`FINAL` схлопывает только строки с **одинаковым ключом сортировки**. Он не спасает, когда новая версия объекта содержит **меньше строк**, чем старая:

- документ перепровели, в ТЧ было 10 строк, стало 7 → строки 8–10 старой версии остаются видимыми («фантомы»);
- документ распровели → у регистратора 0 новых строк, все старые остаются.

Поэтому читать нужно так:

```sql
-- Шапки: FINAL достаточно (одна строка на ключ)
CREATE VIEW mega.v_dokument_postuplenie AS
SELECT * FROM mega.dokument_postuplenie_na_raschetnyy_schet_v2 FINAL
WHERE _is_deleted = 0;

-- ТЧ: живыми считаются только строки той версии, которой является ШАПКА
CREATE VIEW mega.v_dokument_postuplenie_tovary AS
SELECT t.*
FROM mega.dokument_postuplenie_na_raschetnyy_schet_tovary_v2 AS t
INNER JOIN
(
    SELECT ssylka, max(_version) AS v
    FROM mega.dokument_postuplenie_na_raschetnyy_schet_v2
    GROUP BY ssylka
) AS last ON t.ssylka = last.ssylka AND t._version = last.v;

-- Регистры: живые строки — версии, максимальной для данного регистратора
CREATE VIEW mega.v_registr_prodazhi AS
SELECT r.*
FROM mega.registr_nakopleniya_prodazhi_v2 AS r
INNER JOIN
(
    SELECT registrator, max(_version) AS v
    FROM mega.registr_nakopleniya_prodazhi_v2
    GROUP BY registrator
) AS last ON r.registrator = last.registrator AND r._version = last.v
WHERE r._is_deleted = 0;
```

Фантомные (устаревшие) строки при этом просто не видны через view. Физически их подчищает **редкая плановая зачистка** (раз в сутки/неделю, в окно низкой нагрузки) — это единственная оставшаяся мутация в системе, и она плановая, а не на каждой пачке:

```sql
-- Поправка к первой редакции руководства: оконная функция в HAVING в ClickHouse
-- недопустима (окна разрешены только в SELECT/ORDER BY), поэтому «не максимальная
-- версия регистратора» выражается через NOT IN по парам (registrator, max(_version)).
-- Подзапрос вычисляется один раз при постановке мутации; куски, вставленные позже,
-- мутация не трогает — свежие версии не пострадают.
ALTER TABLE mega.registr_nakopleniya_prodazhi_v2
DELETE WHERE (registrator, _version) NOT IN
(
    SELECT registrator, max(_version)
    FROM mega.registr_nakopleniya_prodazhi_v2
    GROUP BY registrator
);
-- или проще: периодический OPTIMIZE TABLE ... FINAL для схлопывания дублей ключей,
-- плюс DELETE по версии — только там, где реально были перепроведения
```

### 1.4. Атомарность «шапка + ТЧ»: порядок вставки — вот и вся транзакция

В ClickHouse нет транзакций между таблицами. Атомарность достигается **порядком фиксации**: шапка вставляется **последней** и играет роль коммита.

Правило для каждой пачки ссылок:

1. Вставить **все табличные части** (каждая ТЧ — свой INSERT) с версией `V`.
2. Только если **все** ТЧ вставились успешно — вставить **шапки** с той же версией `V`.
3. Если любая ТЧ упала — шапку **не вставлять**. Пачка ретраится целиком с той же `V`.

Почему это работает: view для ТЧ (см. 1.3) показывает только строки, чья `_version` совпадает с версией шапки. Пока шапка версии `V` не записана, все уже вставленные ТЧ версии `V` **невидимы** для потребителей — как незакоммиченная транзакция. Упавший на середине прогон не оставляет ни дыр, ни половинчатых документов: читатели продолжают видеть предыдущую целостную версию.

Для регистров аналогично: «коммитом» является сам факт полной вставки регистратора, поэтому действует правило **«регистратор целиком в одном INSERT»** (не резать движения одного регистратора по границе пачки — пачки формировать по регистраторам, см. раздел 2). При ретрае той же пачки с той же `V` дубли схлопнутся движком.

Дополнительно про атомарность одного INSERT: один INSERT, попадающий в одну партицию и не превышающий ~1 млн строк (`max_insert_block_size`), записывается одним куском — целиком или никак. Держите пачки в пределах десятков тысяч строк (это и так нужно по памяти 1С), и на практике каждый INSERT будет атомарен.

## 2. Исправление K-01: регистры — удаление по регистратору, вставка по периоду

### 2.1. Напоминание сути ошибки

Сейчас (строки 176–203, 633–683): выборка движений — по `Период МЕЖДУ &ПериодОт И &ПериодДо` (окно 7 дней), а `ALTER DELETE` — по `registrator IN (...)`, где список регистраторов собран **из строк, попавших в окно**. Расхождение предикатов приводит к двум видам потерь:

1. **Перепроведение со сменой периода.** У документа были движения и в окне, и вне окна (или период сместился за окно). DELETE снесёт **все** движения регистратора, а INSERT вернёт только строки с периодом внутри окна. Движения вне окна потеряны навсегда.
2. **Распроведение.** Движения удалены в 1С → в окне у регистратора 0 строк → регистратор вообще не попадает в список → его устаревшие движения в CH **никогда не удаляются**.

Корень: **предикат удаления обязан совпадать с предикатом вставки**. Правильная единица работы для регистра — **регистратор целиком**, без фильтра по периоду на строках.

### 2.2. Вариант Б (целевой): в схеме раздела 1 ошибка исчезает сама

Если сделан раздел 1, K-01 закрыт автоматически: мы вставляем **все** текущие движения изменённого регистратора с новой версией, view показывает только максимальную версию регистратора, «лишние» старые строки становятся фантомами и зачищаются планово. Распроведённый документ обрабатывается вставкой одной строки-надгробия `_is_deleted = 1` (или просто остаётся на старой версии до плановой зачистки — но тогда надгробие обязательно, иначе view продолжит показывать старую версию: у распроведённого регистратора нет новых строк, и `max(_version)` не сдвинется!).

**Важно для варианта Б:** для регистратора с нулём текущих движений нужно всегда вставлять надгробие — одну строку с ключевыми полями, `_is_deleted = 1` и новой версией. Это единственный способ «сказать» view, что движений больше нет.

### 2.3. Вариант А (быстрый): исправление внутри текущей схемы DELETE+INSERT

Если раздел 1 делается не сразу — K-01 чинится и в текущей схеме. Меняется драйвер выборки: не «строки за период», а «изменённые регистраторы».

**Шаг 1. Получить список изменённых регистраторов** (вместо текущего запроса по периоду). Два источника, объединяемых:

```bsl

	|ИЗ РегистрНакопления." + тРегистрМД.Имя + " КАК Т
	|ГДЕ Т.Период МЕЖДУ &ПериодОт И &ПериодДо
	|
	|ОБЪЕДИНИТЬ
	|
	|ВЫБРАТЬ РАЗЛИЧНЫЕ ВЫРАЗИТЬ(АС.Объект КАК Документ." + ИмяДокументаРегистратора + ")
```

Первая часть ловит документы, чьи движения сейчас лежат в окне. Вторая (по `АудиторскийСлед`, аналогично тому, как уже сделано для документов в `КХ_ПолучитьСсылкиИзБазы_АУ`, строки 468–495) ловит **перепроведённые и распроведённые** документы, даже если их движения ушли из окна или исчезли совсем. Именно вторая часть закрывает оба сценария потерь из 2.1 — и заодно K-04 (сейчас регистры аудиторский след не используют вообще).

**Шаг 3. Для каждой пачки — единый предикат на удаление и вставку:**

```bsl

	// 3.1. ВСЕ текущие движения этих регистраторов — БЕЗ фильтра по периоду
	Запрос = Новый Запрос;
	Запрос.Текст = "ВЫБРАТЬ * ИЗ РегистрНакопления." + тРегистрМД.Имя +
		" ГДЕ Регистратор В (&Регистраторы)";
	Запрос.УстановитьПараметр("Регистраторы", ПачкаРегистраторов);
	// ... выгрузка в массив структур как сейчас ...
	
	// 3.2. DELETE по ЭТОМУ ЖЕ списку регистраторов (дедуплицированному по построению)
	КодУдаления = КХ_УдалитьДанныеПоСписку(СписокНавСсылокРегистраторов, ИмяОсновнойТаблицы, "registrator");
	
	// 3.3. INSERT всех выбранных строк
	Если КодУдаления = 200 И МассивСтрок.Количество() > 0 Тогда
		КХ_ОтправитьДанные(КХ_СформироватьJSON(МассивСтрок), ИмяОсновнойТаблицы);
	КонецЕсли;
	
КонецЦикла;
```

Ключевые свойства:

- предикаты DELETE и INSERT **тождественны** (один и тот же список регистраторов) — потерь больше нет;
- распроведённый документ попадает в список через аудиторский след → его строки удаляются, вставлять нечего — корректно;
- регистратор никогда не режется границей пачки — пачка формируется по регистраторам;
- заодно закрываются: **K-04** (регистры теперь видят перепроведения через аудиторский след), **N-03** (список в DELETE — уже различные регистраторы, а не 5000 строк с повторами; IN сжимается в сотни раз — уходит и риск CH-04 по превышению `max_query_size`), и **значительная часть P-01** (в память тянется не весь период, а пачка регистраторов — это и есть пагинация на уровне запроса, лечащая «превышен безопасный расход памяти»).

Окно останется только в шаге 1 (что считать «изменённым») — это нормально: оно определяет **кого** выгружать, но больше не определяет **какие строки** удалять/вставлять.

**Внимание:** вариант А по-прежнему живёт на мутациях (CH-01 остаётся), а между DELETE и INSERT остаётся неатомарное окно (K-02). Поэтому вариант А — тактика, раздел 1 — стратегия. Код шагов 1–3 при этом не выбрасывается: та же нарезка по регистраторам один в один нужна и для варианта Б, меняется только «DELETE+INSERT» на «INSERT с версией».

<a name="раздел-3"></a>
## 3. Что ещё обязательно поправить в первую очередь (тормозит или обрубает выгрузку)

Отсортировано по влиянию на надёжность прогона. Безопасность (S-01…S-07) по вашей просьбе не трогаем.

### 3.1. 🔴 Таймаут объявлен, но НЕ передан в HTTPСоединение — зависание навсегда осталось

Строки 712 и 718:

```bsl
Таймаут = 300;
...
Соединение = Новый HTTPСоединение(Хост, Порт, , , , , Неопределено);
```

Шестой параметр конструктора `HTTPСоединение` — это таймаут (секунды), седьмой — защищённое соединение. Сейчас на шестой позиции пусто, и переменная `Таймаут` **никуда не используется** — соединение по-прежнему без таймаута. Один подвисший запрос (а с `mutations_sync = 2` и `max_execution_time = 0` в DELETE, строка 379, ждать мутацию можно часами — CH-03) вешает фоновое задание навсегда. Ретраи не помогут: до них дело не дойдёт.

Исправление — одна строка:

```bsl
Соединение = Новый HTTPСоединение(Хост, Порт, , , , Таймаут, Неопределено);
```

Плюс в самом DELETE (строка 379) замените `max_execution_time = 0` на разумный предел, например `max_execution_time = 240` (меньше HTTP-таймаута, чтобы ошибка приходила от CH с текстом, а не обрывом соединения).

### 3.2. 🔴 Новые ретраи бросают исключение, которое убивает весь прогон

Новый `ОтправитьHTTP` после трёх неудач делает `ВызватьИсключение` (строки 734, 742). Но ни один вызов в `КХ_Загрузить_из_ОС` не обёрнут в `Попытка` — исключение вылетает из `КХ_УдалитьДанные`/`КХ_ОтправитьДанные` через все циклы и **роняет всё регламентное задание**. Раньше сбой пачки означал «+1 к счётчику, идём дальше», теперь — «выгрузка обрублена на полпути, оставшиеся таблицы не выгружены вовсе». Это ровно тот симптом, от которого вы хотите уйти.

Второе следствие: проверки `Если Ответ.КодСостояния <> 200` в `КХ_УдалитьДанные` (388–393) и `КХ_ОтправитьДанные` (416–421) стали **мёртвым кодом** — не-2xx оттуда больше не возвращается (либо 2xx, либо исключение). Значит, тело ответа ClickHouse с текстом ошибки теперь не выводится вообще никогда — потеряна главная диагностика.

Исправление (минимальное, сохраняющее ваш контракт «исключение после N попыток»):

1. Обернуть обработку **каждого объекта метаданных** в `Попытка` — сбой одной таблицы не должен трогать остальные (заодно это закрывает K-10: отсутствие `ДатаСоздания` у одного справочника перестанет ронять весь прогон):

```bsl
Для Каждого тДокументМД Из МассивМетаданных Цикл
	Попытка
		// ... вся текущая обработка объекта ...
	Исключение
		тОшибокЗаписиДокументов = тОшибокЗаписиДокументов + 1;
		ЖурналРегистрации.ДобавитьСообщениеДляЖурналаРегистрации(
			"ОбщийМодуль.ВыгрузкаКликхаус.КХ_Загрузить_из_ОС",
			УровеньЖурналаРегистрации.Ошибка, , Строка(тДокументМД),
			ПодробноеПредставлениеОшибки(ИнформацияОбОшибке()));
	КонецПопытки;
КонецЦикла;
```

2. Реализовать оба `// Логируем ... СДЕЛАТЬ!!!` (строки 732, 739) — писать в **журнал регистрации** (не `Сообщить` — в фоновом задании его никто не увидит, A-01/A-06) код состояния, усечённое тело ответа CH (`Лев(Ответ.ПолучитьТелоКакСтроку(), 1000)`), имя хоста и номер попытки. Без этого ретраи маскируют причину: вы узнаете только «после 3 попыток не удалось», но не почему.

3. Убрать мёртвые проверки в вызывающих функциях или (лучше) перенести логирование тела ошибки внутрь `ОтправитьHTTP` на каждую неудачную попытку.

### 3.3. 🔴 Не ретраить ALTER DELETE вслепую

`ОтправитьHTTP` теперь одинаково ретраит и INSERT, и `ALTER TABLE … DELETE`. Для мутаций это опасно: если первая попытка **на самом деле выполнилась**, но ответ не дошёл (таймаут, обрыв), повтор ставит в очередь **вторую такую же мутацию**. Данные не пострадают (предикат тот же), но нагрузка мутациями удваивается-утраивается — вы своими руками усиливаете CH-01, тот самый механизм, который забивает приём данных.

Исправление: добавить в `ОтправитьHTTP` параметр `Знач МаксПопыток = 3` и из `КХ_УдалитьДанные` вызывать с `МаксПопыток = 1` (без ретраев; сбой удаления и так корректно обрабатывается счётчиком и пропуском вставки). Ретраи оставить только для INSERT — они безопасны, а после перехода на раздел 1 станут ещё и идемпотентными. Заодно замените фиксированную паузу 5 с на экспоненциальную: `ЗадержкаСекунд * (2 ^ (НомерПопытки - 1))` — 5, 10, 20 с; при перегрузке CH (TOO_MANY_PARTS) три попытки за 10 секунд бессмысленны.

И про хвост функции: финальный `Возврат Неопределено` (строка 751) недостижим при текущей логике, но если логику тронут — вызывающий код упадёт на `Ответ.КодСостояния`. Замените на `ВызватьИсключение` или удалите ветку.

### 3.4. 🟠 Убрать `wait_for_async_insert = 1` — осталось от удалённого async_insert

Строка 405:

```bsl
ЗапросSQL = "INSERT INTO " + ИмяТаблицы + " SETTINGS wait_for_async_insert = 1, input_format_parallel_parsing = 1 FORMAT JSONEachRow";
```

`async_insert` вы убрали (правильно — CH-02: для крупных пачек он только строил тот самый переполнявшийся буфер-«кэш»), но `wait_for_async_insert = 1` остался. Без `async_insert = 1` эта настройка не делает ничего — мусор, который будет путать при отладке. Оставьте:

```bsl
ЗапросSQL = "INSERT INTO " + ИмяТаблицы + " FORMAT JSONEachRow";
```

(`input_format_parallel_parsing` включён в CH по умолчанию, указывать не обязательно.)

### 3.5. 🟠 Память 1С: регистры по-прежнему материализуют весь период (P-01)

`КХ_ПолучитьДанныеРегистровИзБазы_АУ` (633–683) всё так же делает `ВЫБРАТЬ *` за всё окно и `Выгрузить()` целиком в память; `РазмерПачки` в запрос не попадает (переменная `РазмерПачкиСтрокой` на строке 635 — мёртвый код, удалите). `РазбитьМассив` потом режет **уже загруженный** массив — памяти это не экономит ни байта. Это первопричина «превышен безопасный расход памяти за один серверный вызов».

Исправление = раздел 2, шаги 2–3: пагинация по пачкам регистраторов **на уровне запроса**. В память одновременно попадает одна пачка, а не весь период. Отдельного исправления не требуется — не делайте его дважды.

Для документов и справочников пагинация по ссылкам уже фактически есть (данные тянутся по пачке ссылок), но пачка в 5000 ссылок × все колонки × ТЧ (P-07) — много. Пока не перешли на потоковую выборку, просто уменьшите `РазмерПачки` до 500–1000 (строки 7, 25, 43) — это три числа, а пиковая память упадёт на порядок. Выгрузка станет чуть медленнее — по вашему же приоритету («пусть не быстрой, но надёжной») это правильный размен.

### 3.6. 🟠 Защита от параллельного запуска (A-02)

Если прогон завис (3.1) или идёт дольше интервала расписания, стартует второй — и они начинают наперегонки удалять и вставлять в одни таблицы: гонки, взаимное затирание, двойной шторм мутаций. Минимальное исправление в начале `КХ_Загрузить_из_ОС`:

```bsl
Активные = ФоновыеЗадания.ПолучитьФоновыеЗадания(
	Новый Структура("Состояние", СостояниеФоновогоЗадания.Активно));
Для Каждого Задание Из Активные Цикл
	Если СтрНачинаетсяС(Задание.ИмяМетода, "ВыгрузкаКликхаус.")
		И Задание.УникальныйИдентификатор <> ИдентификаторТекущегоЗадания Тогда
		Сообщить("Выгрузка уже выполняется — выходим");
		Возврат;
	КонецЕсли;
КонецЦикла;
```

(вариант — семафор через константу/регистр с отметкой времени и защитой от «вечно занято» по TTL).

### 3.7. 🟡 Пустые ТЧ: мутация + HTTP-запрос на каждую ТЧ каждой пачки впустую (CH-08)

Сейчас для каждой ТЧ каждой пачки безусловно выполняются `КХ_УдалитьДанные` (мутация!) и `КХ_ОтправитьДанные` — даже когда строк ТЧ нет вовсе. У справочников с тремя пустыми ТЧ это тройная бесполезная мутация на пачку. Исправление:

- вставку пропускать при пустых данных: в начале `КХ_ОтправитьДанные` — `Если ПустаяСтрока(СтрокаJSON) Тогда Возврат 200; КонецЕсли;`
- удаление, пока живёт схема DELETE+INSERT, пропускать **нельзя** (старые строки могли остаться, а новых нет) — но после перехода на раздел 1 исчезнет и оно.

### 3.8. 🟡 Хвост K-07: пустые строки всё ещё превращаются в NULL

Внешние проверки вы поправили, но внутри `КХ_ПреобразоватьЗначение` остались `ЗначениеЗаполнено`:

- строка 896: `Тип("Строка") И ЗначениеЗаполнено(...)` — пустая строка `""` не попадает ни в одну ветку → функция вернёт `Неопределено` → в CH уйдёт `null` вместо `""`;
- строка 917: то же для `УникальныйИдентификатор` (нулевой UUID → null; возможно, так и задумано — тогда зафиксируйте комментарием);
- значения типа `NULL` из запроса (поля через точку от «битых» ссылок) не равны `Неопределено` — проходят внешнюю проверку, в `КХ_ПреобразоватьЗначение` не попадают ни в одну ветку и тоже уезжают как `null` (тут это как раз корректно, но пусть будет явная ветка).

Исправление: в ветке `Строка` убрать `И ЗначениеЗаполнено(тЗначение)`; в начале функции добавить явную ветку `Если тЗначение = NULL Тогда Возврат Неопределено; КонецЕсли;`. И включите в INSERT-URL `input_format_null_as_default=1` — тогда случайный `null` в числовой колонке не завалит всю пачку.

### 3.9. 🟡 Быстрые победы по скорости (снижают время прогона и окно для сбоев)

Чем дольше прогон, тем больше шанс поймать обрыв/перезапуск. Три дешёвые правки:

1. **JSON через массив, а не конкатенацию** (P-04, строка 703): `СтрокаРезультат = СтрокаРезультат + ...` на больших пачках — O(n²) по памяти/времени. Собирайте строки в массив и в конце `СтрСоединить(МассивСтрок, Символы.ПС)`.
2. **Кэш транслитерации** (P-03): `КХ_ТранслитерироватьСтроку` пересоздаёт соответствие из 33 букв и гоняет посимвольный алгоритм **для каждой колонки каждой строки** (миллионы вызовов за прогон). Достаточно один раз на таблицу построить `Соответствие ИмяКолонки → snake_case` перед циклом по строкам (колонки-то одни и те же) — выигрыш в разы на широких таблицах.
3. **Файл-дамп на сервере** (строка 295): запись `C:\temp\Выгрузка Кликхаус.json` при каждой ошибке вставки документов — на сервере 1С может не быть `C:\temp`, а при двух параллельных фоновых заданиях будет драка за файл. Либо уберите, либо пишите во `ПолучитьИмяВременногоФайла()` и путь — в журнал регистрации.

### 3.10. ⚪ Прибраться

- Мёртвая `РазмерПачкиСтрокой` (строка 635) — удалить.
- Закомментированные `//Продолжить;` (254, 261, 320, 327) — решить и удалить.
