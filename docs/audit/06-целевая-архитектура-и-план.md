# Целевая архитектура и план: надёжная выгрузка 1С → ClickHouse

Требование заказчика: **надёжно, пусть и не быстро**. Этот документ описывает, как перестроить модуль так, чтобы (1) один серверный вызов 1С не выходил за память и (2) ClickHouse не вставал от мутаций и переполнения буфера, а сбои автоматически долечивались.

Читать после разделов [03 (память 1С)](03-производительность-и-память-1с.md) и [04 (ClickHouse)](04-надежность-clickhouse.md). Редакция учитывает поправку Ф-03 контрольного прохода (см. [07](07-повторный-аудит-и-поправки.md)): чтение табличных частей и регистров через один лишь `FINAL` некорректно — ниже приведён правильный паттерн.

---

## Два принципа, снимающих оба симптома

### Принцип 1. Регулярная загрузка — только `INSERT`, без мутаций

Отказаться от `ALTER TABLE … DELETE` в ежедневной работе (первопричина CH-01). Вместо «удалить старое → вставить новое» — **вставлять новую версию строки и позволить ClickHouse схлопнуть старые в фоне**.

Инструмент — движок **`ReplacingMergeTree`** с колонкой версии. Он при фоновом слиянии оставляет строку с максимальной версией по ключу сортировки; чтение идёт через представления с дедупликацией (правила — ниже, для шапок и для ТЧ/регистров они разные).

Выгода:
- регулярная работа = поток `INSERT` крупными кусками → нет мутаций, нет шторма кусков, ClickHouse не отказывает во вставках;
- **идемпотентность**: повторная вставка той же пачки безопасна (победит последняя версия) → ретраи и перезапуски не создают дублей и не оставляют дыр (снимает K-02);
- сбой на полпути не разрушает данные: читатели продолжают видеть предыдущую согласованную версию (см. порядок «ТЧ → шапка» ниже).

### Принцип 2. Память ограничена размером пачки на каждом шаге

Ни один серверный вызов не должен материализовывать в память больше одной пачки. Пагинация начинается **на выборке** из 1С, а не на отправке (снимает P-01). Крупные объекты и длинные периоды дробятся на фоновые задания.

## Целевая схема данных в ClickHouse

Для каждой таблицы `mega.*` — движок `ReplacingMergeTree(version)`; ключ сортировки включает бизнес-ключ строки.

**Справочники и документы (шапка):**
```sql
CREATE TABLE mega.dokument_realizatsiya_tovarov_uslug
(
    uuid            String,               -- UUID ссылки: стабильный ключ
    ssylka          String,               -- навигационная ссылка (представление), опционально
    -- ... прикладные реквизиты явным списком, с корректными типами ...
    summa_dokumenta Decimal(18,2),
    data            DateTime('UTC'),
    pometka_udaleniya UInt8 DEFAULT 0,    -- soft-delete (K-08)
    _version        UInt64,               -- версия выгрузки (напр. миллисекунды запуска)
    _is_deleted     UInt8 DEFAULT 0       -- для ReplacingMergeTree(_version, _is_deleted)
)
ENGINE = ReplacingMergeTree(_version, _is_deleted)
ORDER BY uuid
PARTITION BY toYYYYMM(data);
```

> **Требование версии:** параметр `is_deleted` у `ReplacingMergeTree(ver, is_deleted)` доступен с **ClickHouse 23.2**. На более старых версиях используйте `ReplacingMergeTree(_version)`, а `_is_deleted` оставьте обычной колонкой с фильтром в представлениях.

**Табличные части:** ключ — `(uuid_vladeltsa, nomer_stroki)`, та же `_version`, что и у шапки пачки:
```sql
CREATE TABLE mega.dokument_realizatsiya_tovarov_uslug_tovary
(
    uuid           String,     -- UUID документа-владельца
    nomer_stroki   UInt32,
    -- ... реквизиты строки ...
    _version       UInt64,
    _is_deleted    UInt8 DEFAULT 0
)
ENGINE = ReplacingMergeTree(_version, _is_deleted)
ORDER BY (uuid, nomer_stroki)
PARTITION BY <по владельцу или по месяцу документа>;
```

**Регистры:** ключ сортировки — по регистратору и координатам строки движения; версия — по запуску:
```sql
CREATE TABLE mega.registr_nakopleniya_prodazhi
(
    registrator    String,     -- UUID регистратора
    period         DateTime('UTC'),
    nomer_stroki   UInt32,
    -- ... измерения и ресурсы (включая vid_dvizheniya / числовой знак — см. N-01) ...
    _version       UInt64,
    _is_deleted    UInt8 DEFAULT 0
)
ENGINE = ReplacingMergeTree(_version, _is_deleted)
ORDER BY (registrator, period, nomer_stroki)
PARTITION BY toYYYYMM(period);
```

### Чтение последней версии: где `FINAL` достаточен, а где нет (поправка Ф-03)

`FINAL` дедуплицирует только строки **с одинаковым ключом сортировки**. Поэтому:

- **Шапки** (ключ = `uuid`, одна строка на объект): `FINAL` полностью решает задачу.
- **ТЧ и регистры**: `FINAL` **НЕ убирает строки, которых в новой версии больше нет**. Если ТЧ сократилась с 10 строк до 8, строки 9–10 старой версии имеют ключи, которых нет в новой, — им не с чем схлопнуться, и они останутся видимыми («фантомы»). То же с движениями регистра, сменившими `period` при перепроведении.

Правильные представления:

```sql
-- Шапки: FINAL достаточен
(см. пример ниже)
CREATE VIEW mega.v_dokument_x AS
SELECT * FROM mega.dokument_x FINAL WHERE _is_deleted = 0;

-- ТЧ: читать только строки ПОСЛЕДНЕЙ версии владельца,
-- причём версия правды берётся ИЗ ШАПКИ (шапка = «коммит», см. порядок вставки)
CREATE VIEW mega.v_dokument_x_tovary AS
SELECT t.*
FROM mega.dokument_x_tovary AS t FINAL          -- FINAL гасит дубли от повторов одной версии
INNER JOIN
(
    SELECT uuid, max(_version) AS v
    FROM mega.dokument_x                         -- максимум по таблице ШАПОК
    GROUP BY uuid
) AS last ON t.uuid = last.uuid AND t._version = last.v;

-- Регистры: аналогично по registrator; max(_version) можно брать по самой таблице,
-- ЕСЛИ соблюдается правило «регистратор целиком в одном INSERT» (ниже)
CREATE VIEW mega.v_prodazhi AS
SELECT t.*
FROM mega.registr_nakopleniya_prodazhi AS t FINAL
INNER JOIN
(
    SELECT registrator, max(_version) AS v
    FROM mega.registr_nakopleniya_prodazhi
    GROUP BY registrator
) AS last ON t.registrator = last.registrator AND t._version = last.v
WHERE t._is_deleted = 0;
```

> На очень больших таблицах вместо `FINAL` для шапок можно использовать `argMax(col, _version)` с `GROUP BY ключ`, либо плановый `OPTIMIZE … FINAL` на «остывших» партициях — но для ТЧ/регистров фильтр по max-версии владельца обязателен в любом случае: ни `FINAL`, ни `OPTIMIZE` фантомы не убирают (у них другие ключи).

**Гигиена фантомов.** Физически строки старых версий с «осиротевшими» ключами остаются в таблице (через представления они не видны). Раз в неделю–месяц, вне пиков, их можно чистить плановым `DELETE … WHERE (uuid, _version) NOT IN (SELECT uuid, max(_version) … GROUP BY uuid)` — это единственная допустимая мутация в целевой схеме: редкая, плановая, не на горячем пути.

### Как эта схема решает старые проблемы

| Было | Стало |
|---|---|
| CH-01 шторм мутаций DELETE | Только INSERT; единственная мутация — редкая плановая чистка фантомов |
| CH-02 «кэш» async_insert | Синхронная вставка пачками |
| K-01 потеря движений регистра | Регистратор выгружается целиком новой версией; старые версии отсекаются представлением по max-версии |
| K-02 дыра при сбое вставки | Идемпотентность: повтор безопасен, дыр нет |
| K-03 рассинхрон шапки и ТЧ | Одна `_version` на шапку и все ТЧ; вставка «ТЧ → шапка»; чтение ТЧ по версии шапки |
| K-08 удалённые остаются | soft-delete: `_is_deleted=1` новой версией |
| CH-04 гигантский DELETE `IN` | Нет DELETE на горячем пути вовсе |

## Идемпотентный цикл загрузки одного объекта

Ключевая замена «DELETE→INSERT» на «версионный INSERT». Два жёстких правила порядка:

1. **Внутри пачки документов/справочников: сначала все табличные части, ПОСЛЕДНЕЙ — шапка.** Шапка играет роль «коммита» версии: представления ТЧ привязаны к max-версии шапки, поэтому пока шапка не вставлена, читатели видят предыдущую согласованную версию целиком. Частичный сбой (ТЧ легли, шапка нет) невидим и долечивается следующим запуском (новая версия полностью).
2. **Пачка регистров режется строго по границам регистраторов**: все движения одного регистратора — всегда в одном INSERT. Тогда версия атомарна на регистратора, и представление по max-версии регистратора всегда отдаёт целостный набор его строк.

```
Штамп версии на весь запуск: _version = миллисекунды старта запуска
(одинаковы для шапки и её ТЧ; при ретрае внутри запуска — та же версия, дубли схлопнутся).

Для каждого объекта (документ/справочник/регистр):
    Для каждой пачки (страницы) ключей:
        Попытка
            Выбрать данные шапки и всех ТЧ пачки (объём ограничен пачкой)
            Сформировать JSON потоково
            Отправить INSERT-ы ТЧ (async_insert=0, с ретраями 2с/4с/8с/16с)
            Отправить INSERT шапки ПОСЛЕДНИМ (те же ретраи)
            Если шапка не доставлена → вся пачка помечается «повторить»
            (читатели продолжают видеть старую согласованную версию)
            Зафиксировать в состоянии: объект X, страница P доставлена
        Исключение
            Залогировать; пометить страницу «повторить в следующий запуск»; продолжить со следующей
```

Никаких удалений на горячем пути. Повтор упавшей пачки в следующем запуске просто добавляет более свежую версию — данные самозалечиваются.

**Обработка удалений (K-08):** подписка на удаление объектов 1С (или отдельный журнал) → вставка версии с `_is_deleted = 1`. Физически в ClickHouse ничего не мутируется.

## Пагинация и память (решение P-01)

### Регистры — страницами по регистраторам, не «весь период в память»

Вместо `ВЫБРАТЬ * … Период МЕЖДУ` со `Выгрузить()` целиком:

1. Получить **список регистраторов**, изменённых за период (через аудиторский след / период регистратора) — только ссылки, компактно.
2. Резать регистраторов на страницы (например, по 200–500), **всегда целыми регистраторами** — движения одного регистратора никогда не делятся между пачками/INSERT-ами.
3. Для каждой страницы выбирать движения **только этих регистраторов целиком** (без фильтра по периоду!) и сразу гнать в JSON/INSERT, освобождая память.

Так снимаются и P-01 (память), и K-04 (правки задним числом попадают: отбор по изменённым регистраторам, а не по периоду движений), и K-01 (регистратор обновляется целиком).

### Документы/справочники — обрабатывать пачку и сразу освобождать

Список ссылок уже режется на пачки. Нужно:
- не собирать весь массив данных периода — обрабатывать пачку ссылок за раз (выбрать → JSON → отправить → обнулить);
- саму выборку ссылок тоже ограничивать (курсор/`ПЕРВЫЕ N` по дате изменения) при очень больших периодах;
- размер пачки задавать с учётом «веса» объекта (документы с большими ТЧ — меньше, см. P-07).

### Дробление на фоновые задания

Длинный период или тяжёлый объект — разбивать на несколько фоновых заданий (`ДлительныеОперации`/`ФоновыеЗадания`): по объекту и по под-периоду. Каждое задание — свой короткий серверный вызов с ограниченной памятью; расписание запускает их последовательно/с ограничением параллелизма (с учётом A-02 — без наложения на одну таблицу).

## Потоковая сборка JSON (решение P-04) и кэш имён (P-03)

- Формировать JSON пачки не конкатенацией, а накоплением фрагментов в массив с финальным `СтрСоединить`, либо писать в один поток `ЗаписьJSON`. Идеально — писать сразу в тело HTTP-запроса пачки.
- Имена колонок транслитерировать **один раз на объект** (построить карту «имя реквизита → snake_case») и переиспользовать; при построении карты проверять уникальность имён (N-08). Таблицу транслитерации инициализировать один раз, а не в каждом вызове.
- В преобразовании значений: не терять `0`/`Ложь`/`""` (K-07), обрабатывать все ссылочные типы (K-06) и системные перечисления — в первую очередь вид движения (N-01), перечисления выгружать именем значения, а не синонимом (N-07).

## Настройки вставки в ClickHouse (решение CH-01/CH-02/CH-03)

Регулярная вставка:
```sql
INSERT INTO <table> SETTINGS async_insert = 0 FORMAT JSONEachRow
```
- `async_insert = 0` — синхронно, детерминированный результат на пачку (нет «кэша»).
- Никаких `ALTER … DELETE` в регулярном цикле.
- Крупные пачки (5000+ строк) — это то, что ClickHouse любит: один INSERT = один-несколько кусков.

HTTP на стороне 1С:
- задать **таймаут** соединения (например, 300 с) — чтобы не висеть вечно (CH-03/CH-05);
- переиспользовать соединение в пределах таблицы (P-09);
- аутентификация — **заголовками** `X-ClickHouse-User`/`X-ClickHouse-Key` по **HTTPS** (S-02/S-03), пароль не в URL.

Ключи — **UUID** (CH-10): короткие, стабильные, компактные.

## Состояние, ретраи, наблюдаемость (решение A-01/A-06)

- **Регистр состояния выгрузки** (регистр сведений): по каждому объекту — последняя успешная граница/страница, статус, число строк, код последней ошибки, время. Окно следующего запуска — **от последней успешной границы**, а не фиксированные «7 дней от сейчас» — иначе простой дольше окна теряет инкремент безвозвратно (N-05). Это же снимает P-08 (нет семикратной перевыгрузки).
- **Ретраи** с экспоненциальной паузой на каждую сетевую операцию; при исчерпании — пометка «повторить в следующем запуске», а не потеря. Благодаря идемпотентности ретраи безопасны всегда.
- **Журнал регистрации** — единая обёртка: старт/финиш запуска (с идентификатором), событие на объект (выбрано/отправлено/ошибок), тело ответа ClickHouse при ошибке (усечённо), уровни. `Сообщить` — только для интерактивной отладки.
- **Метрики** — время и объёмы по таблицам для отслеживания деградации; контрольные запросы к `system.mutations` (должно быть пусто на горячем пути) и `system.parts`.
- **Защита от параллельного запуска** (A-02) — управляемая блокировка/флаг «идёт выгрузка».

## Рефакторинг кода (решение A-03/A-04/A-05)

- Свести три ветки и три процедуры `Выгрузка_День_*` к одной обобщённой, параметризованной типом и списком; состав полей определять по метаданным конкретного объекта (снимает K-05/K-10/N-02); явная ветка «неподдерживаемый тип — ошибка в журнал» (N-09).
- Один хелпер «запрос → потоковый JSON пачки».
- **Списки метаданных и параметры** (размер пачки, окно, вкл/выкл, приоритет, префикс БД) — вынести в **регистр настроек**, управляемый без релиза.
- Магические константы — в именованные настройки; даты — через функции периодов, а не арифметику секунд.
- Секреты — в защищённое хранилище (S-01).
- DDL ClickHouse и контракт типов — в репозиторий (A-08); тесты чистых функций + dry-run (A-09).

## Поэтапный план внедрения

Порядок — по убыванию риска/выгоды. Каждый этап самостоятелен и оставляет систему работоспособной.

### Фаза 0 — Безопасность и «стоп-кран» (в течение 1–2 дней)
- 🔴 Сменить пароль `mega_user` (текущий скомпрометирован).
- 🔴 Закрыть порт 58123 файрволом, доступ только с сервера 1С.
- 🔴 Сверить данные балансовых регистров в CH на NULL-вид движения (N-01) — оценить масштаб поражения данных.
- 🟠 Задать таймаут HTTP-соединения в `ОтправитьHTTP`.
- 🟠 Обернуть каждую сетевую операцию в `Попытка/Исключение` с логированием (CH-05).
- 🟡 Убрать запись в `C:\temp` (S-05).

*Результат:* прекращается утечка и «падение всего задания от одного чиха»; известен масштаб проблемы N-01.

### Фаза 1 — Надёжность и корректность типов без смены схемы (неделя 1)
- Ретраи с паузами вокруг вставок/удалений; сбойные пачки — в «повторить», не терять.
- Отказ от `async_insert` (`= 0`) — убрать «кэш» (CH-02).
- Полное журналирование в журнал регистрации, включая тело ответа CH и ошибки вставки (A-06).
- Защита от параллельного запуска (A-02).
- Исправить потери в типах одним пакетом: **N-01 (вид движения), K-07 (`0`/`Ложь`/`""`), K-06 (все ссылочные типы), N-07 (имя перечисления вместо синонима)** — с dry-run сравнением JSON «до/после»; по итогам — перезаливка поражённых таблиц.
- Окно выгрузки — от последнего успешного запуска (N-05).

*Результат:* заметно меньше потерь и «зависаний», данные типов корректны; проблема мутаций и памяти ещё есть.

### Фаза 2 — Схема без мутаций (недели 2–3)
- Развернуть таблицы `ReplacingMergeTree(_version, _is_deleted)` (CH ≥ 23.2; иначе без параметра is_deleted) — миграция DDL в репозитории.
- Перевести загрузку на версионный INSERT с порядком «ТЧ → шапка» и правилом «регистратор целиком в одном INSERT», **убрать `ALTER … DELETE`** из регулярного цикла (CH-01, K-01, K-02, K-03).
- Представления: шапки — `FINAL`; ТЧ и регистры — **по max-версии владельца** (поправка Ф-03); переключить потребителей на них.
- soft-delete для удалённых объектов (K-08); плановая чистка фантомов раз в неделю–месяц.
- Ключи — UUID (CH-10, K-09).

*Результат:* ClickHouse перестаёт вставать; регулярная работа — только вставки; идемпотентность и самозалечивание; читатели не видят ни фантомов, ни полузаписанных версий.

### Фаза 3 — Память и масштаб (недели 3–4)
- Пагинация выборок: регистры — страницами по регистраторам целиком (P-01, K-01, K-04); документы/справочники — обработка пачки с освобождением памяти.
- Потоковая сборка JSON (P-04); кэш имён колонок с контролем уникальности (P-03, N-08).
- Дробление на фоновые задания по объекту/под-периоду.
- Явные списки полей вместо `ВЫБРАТЬ *` (P-05, CH-06); временные таблицы ключей (P-06); валидация диапазонов дат (N-04).

*Результат:* один серверный вызов не выходит за память; большие объёмы грузятся устойчиво.

### Фаза 4 — Сопровождаемость (далее)
- Рефакторинг дублей в обобщённые процедуры (A-03).
- Настройки выгрузки в данных (A-04, A-05).
- Регистр состояния и метрики (A-01); инкремент от последней успешной границы (P-08, N-05).
- Тесты чистых функций и dry-run (A-09); зафиксировать зависимость `Сервисный` и DDL (A-08).

## Чек-лист приёмки «надёжно»

Считаем цель достигнутой, когда:

- [ ] Регулярная выгрузка **не выполняет ни одной мутации** `ALTER … DELETE` (проверка по `system.mutations`).
- [ ] Число активных кусков стабильно, ошибок `TOO_MANY_PARTS` нет под штатной нагрузкой.
- [ ] `async_insert` выключен; вставки синхронные, результат каждой пачки детерминирован.
- [ ] Сетевой сбой/недоступность ClickHouse **не роняет** прогон: сбойные пачки помечаются к повтору и долечиваются; повтор не создаёт дублей и дыр.
- [ ] Один серверный вызов 1С ограничен по памяти размером пачки; большие объёмы разбиты на фоновые задания.
- [ ] Значения `0`/`Ложь`/`""` не теряются; **вид движения и прочие системные перечисления выгружаются (N-01)**; ссылки всех типов сериализуются; даты и таймзоны согласованы с типами колонок.
- [ ] Перепроведение документа задним числом корректно отражается в регистрах (K-01/K-04).
- [ ] **Сокращение числа строк ТЧ / смена периода движений не оставляет фантомных строк в представлениях** (ловушка FINAL учтена: чтение по max-версии владельца, порядок «ТЧ → шапка», регистратор целиком в одном INSERT).
- [ ] Простой заданий любой длительности не теряет инкремент (окно от последней успешной границы — N-05).
- [ ] Секреты не в коде и не в git; обмен по HTTPS; порт закрыт от внешнего мира.
- [ ] Все значимые события и ошибки — в журнале регистрации; есть метрики по таблицам.
- [ ] Есть защита от параллельного запуска.

## Кратко

Два симптома заказчика — это две стороны «слишком много за один заход»: память серверного вызова 1С (полная материализация периода) и приём ClickHouse (шторм мутаций + async-буфер). Оба лечатся сменой модели: **регулярная работа — только идемпотентный `INSERT` в `ReplacingMergeTree` (вставка «ТЧ → шапка», регистратор целиком, чтение по max-версии владельца), а выборка и отправка — строго пачками с ретраями и учётом состояния**. Это даёт именно то, что просили: не обязательно быстро, но надёжно и предсказуемо, с автоматическим долечиванием сбоев.
