# Целевая архитектура и план: надёжная выгрузка 1С → ClickHouse

Требование заказчика: **надёжно, пусть и не быстро**. Этот документ описывает, как перестроить модуль так, чтобы (1) один серверный вызов 1С не выходил за память и (2) ClickHouse не вставал от мутаций и переполнения буфера, а сбои автоматически долечивались.

Читать после разделов [03 (память 1С)](03-производительность-и-память-1с.md) и [04 (ClickHouse)](04-надежность-clickhouse.md) — здесь их проблемы решаются конструктивно.

---

## Два принципа, снимающих оба симптома

### Принцип 1. Регулярная загрузка — только `INSERT`, без мутаций

Отказаться от `ALTER TABLE … DELETE` в ежедневной работе (первопричина CH-01). Вместо «удалить старое → вставить новое» — **вставлять новую версию строки и позволить ClickHouse схлопнуть старые в фоне**.

Инструмент — движок **`ReplacingMergeTree`** с колонкой версии. Он при фоновом слиянии оставляет строку с максимальной версией по ключу сортировки. Чтение всегда идёт с `FINAL` или через агрегацию по последней версии — тогда старые версии не видны, даже пока не схлопнулись.

Выгода:
- регулярная работа = поток `INSERT` крупными кусками → нет мутаций, нет шторма кусков, ClickHouse не отказывает во вставках;
- **идемпотентность**: повторная вставка той же пачки безопасна (победит последняя версия) → ретраи и перезапуски не создают дублей и не оставляют дыр (снимает K-02);
- сбой на полпути не разрушает данные: в худшем случае временно сосуществуют две версии, которые схлопнутся при слиянии/`FINAL`.

### Принцип 2. Память ограничена размером пачки на каждом шаге

Ни один серверный вызов не должен материализовывать в память больше одной пачки. Пагинация начинается **на выборке** из 1С, а не на отправке (снимает P-01). Крупные объекты и длинные периоды дробятся на фоновые задания.

## Целевая схема данных в ClickHouse

Для каждой таблицы `mega.*` — движок `ReplacingMergeTree(version)`; ключ сортировки включает бизнес-ключ строки.

**Справочники и документы (шапка):**
```sql
CREATE TABLE mega.dokument_realizatsiya_tovarov_uslug
(
    uuid            String,               -- UUID ссылки: стабильный ключ
    ssylka          String,               -- навигационная ссылка (представление), опционально
    -- ... прикладные реквизиты явным списком, с корректными типами ...
    summa_dokumenta Decimal(18,2),
    data            DateTime('UTC'),
    pometka_udaleniya UInt8 DEFAULT 0,    -- soft-delete (K-08)
    _version        UInt64,               -- версия выгрузки (напр. миллисекунды запуска)
    _is_deleted     UInt8 DEFAULT 0       -- для ReplacingMergeTree(_version, _is_deleted)
)
ENGINE = ReplacingMergeTree(_version, _is_deleted)
ORDER BY uuid
PARTITION BY toYYYYMM(data);
```

**Табличные части:** ключ — `(uuid_vladeltsa, nomer_stroki)`, та же `_version`, что и у шапки пачки (консистентность шапки и строк, снимает K-03):
```sql
CREATE TABLE mega.dokument_realizatsiya_tovarov_uslug_tovary
(
    uuid           String,     -- UUID документа-владельца
    nomer_stroki   UInt32,
    -- ... реквизиты строки ...
    _version       UInt64,
    _is_deleted    UInt8 DEFAULT 0
)
ENGINE = ReplacingMergeTree(_version, _is_deleted)
ORDER BY (uuid, nomer_stroki)
PARTITION BY <по владельцу или по месяцу документа>;
```

**Регистры:** ключ сортировки — по регистратору и координатам строки движения; версия — по запуску:
```sql
CREATE TABLE mega.registr_nakopleniya_prodazhi
(
    registrator    String,     -- UUID регистратора
    period         DateTime('UTC'),
    nomer_stroki   UInt32,
    -- ... измерения и ресурсы ...
    _version       UInt64,
    _is_deleted    UInt8 DEFAULT 0
)
ENGINE = ReplacingMergeTree(_version, _is_deleted)
ORDER BY (registrator, period, nomer_stroki)
PARTITION BY toYYYYMM(period);
```

**Чтение аналитиками — через представления с дедупликацией** (чтобы не видеть старые версии и soft-deleted):
```sql
CREATE VIEW mega.v_prodazhi AS
SELECT * FROM mega.registr_nakopleniya_prodazhi FINAL WHERE _is_deleted = 0;
```
> `FINAL` дедуплицирует по ключу на лету. На больших таблицах он дороже обычного чтения — где это критично, вместо `FINAL` используют `argMax(col, _version)` с `GROUP BY <ключ>` в самом представлении, либо `OPTIMIZE … FINAL` по расписанию на «остывших» партициях.

### Как эта схема решает старые проблемы

| Было | Стало |
|---|---|
| CH-01 шторм мутаций DELETE | Только INSERT; удалений нет |
| CH-02 «кэш» async_insert | Синхронная вставка пачками |
| K-01 потеря движений регистра | Обновляем регистратор целиком новой версией; старые версии схлопываются, ничего не теряется |
| K-02 дыра при сбое вставки | Идемпотентность: повтор безопасен, дыр нет |
| K-03 рассинхрон шапки и ТЧ | Одна `_version` на шапку и все ТЧ пачки; читаем консистентную версию |
| K-08 удалённые остаются | soft-delete: `_is_deleted=1` новой версией |
| CH-04 гигантский DELETE `IN` | Нет DELETE вовсе |

## Идемпотентный цикл загрузки одного объекта

Ключевая замена «DELETE→INSERT» на «версионный INSERT»:

```
Штамп версии на весь запуск: _version = миллисекунды старта запуска (одинаковы для шапки и её ТЧ).

Для каждого объекта (документ/справочник/регистр):
    Для каждой пачки (страницы) ключей:
        Попытка
            Данные = выбрать пачку из 1С (уже ограничена по объёму)
            JSON   = сформировать построчно (потоково)
            Отправить INSERT (async_insert=0) с _version запуска
            Если код <> 200 → ретрай с паузой (2с,4с,8с,16с), затем пометить пачку "повторить" и продолжить
            Для каждой ТЧ пачки: то же самое с той же _version
            Зафиксировать в состоянии: объект X, страница P доставлена
        Исключение
            Залогировать; пометить страницу "повторить в следующий запуск"; продолжить со следующей
```

Никаких удалений. Устаревшие версии уходят фоновым слиянием / при `FINAL`. Повтор упавшей пачки в следующем запуске просто добавляет более свежую версию — данные самозалечиваются.

**Обработка удалений (K-08):** подписка на удаление объектов 1С (или отдельный журнал) → вставка версии с `_is_deleted = 1`. Физически в ClickHouse ничего не мутируется.

## Пагинация и память (решение P-01)

### Регистры — страницами по регистраторам, не «весь период в память»

Вместо `ВЫБРАТЬ * … Период МЕЖДУ` со `Выгрузить()` целиком:

1. Получить **список регистраторов**, изменённых за период (через аудиторский след / период регистратора) — только ссылки, компактно.
2. Резать регистраторов на страницы (например, по 200–500 регистраторов).
3. Для каждой страницы выбирать движения **только этих регистраторов** и сразу гнать в JSON/INSERT, освобождая память.

Так снимается и P-01 (память), и K-04 (правки задним числом попадают, т.к. отбор по изменённым регистраторам, а не по периоду движений), и K-01 (регистратор обновляется целиком).

### Документы/справочники — обрабатывать пачку и сразу освобождать

Список ссылок уже режется на пачки. Нужно:
- не собирать весь `МассивСтруктур` периода — обрабатывать пачку ссылок за раз (выбрать → JSON → отправить → обнулить);
- саму выборку ссылок тоже ограничивать (курсор/`ПЕРВЫЕ N` по дате изменения) при очень больших периодах;
- размер пачки задавать с учётом «веса» объекта (документы с большими ТЧ — меньше, см. P-07).

### Дробление на фоновые задания

Длинный период или тяжёлый объект — разбивать на несколько фоновых заданий (`ДлительныеОперации`/`ФоновыеЗадания`): по объекту и по под-периоду. Каждое задание — свой короткий серверный вызов с ограниченной памятью; расписание запускает их последовательно/с ограничением параллелизма (с учётом A-02 — без наложения на одну таблицу).

## Потоковая сборка JSON (решение P-04) и кэш имён (P-03)

- Формировать JSON пачки не конкатенацией, а накоплением фрагментов в массив с финальным `СтрСоединить`, либо писать в один поток `ЗаписьJSON`. Идеально — писать сразу в тело HTTP-запроса пачки.
- Имена колонок транслитерировать **один раз на объект** (построить карту «имя реквизита → snake_case») и переиспользовать во всех строках. Таблицу транслитерации инициализировать один раз, а не в каждом вызове.

## Настройки вставки в ClickHouse (решение CH-01/CH-02/CH-03)

Регулярная вставка:
```sql
INSERT INTO <table> SETTINGS async_insert = 0 FORMAT JSONEachRow
```
- `async_insert = 0` — синхронно, детерминированный результат на пачку (нет «кэша»).
- Никаких `ALTER … DELETE` в регулярном цикле.
- Крупные пачки (5000+ строк) — это то, что ClickHouse любит: один INSERT = один-несколько кусков.

HTTP на стороне 1С:
- задать **таймаут** соединения (например, 300 с) — чтобы не висеть вечно (CH-03/CH-05);
- переиспользовать соединение в пределах таблицы (P-09);
- аутентификация — **заголовками** `X-ClickHouse-User`/`X-ClickHouse-Key` по **HTTPS** (S-02/S-03), пароль не в URL.

Ключи — **UUID** (CH-10): короткие, стабильные, компактные.

## Состояние, ретраи, наблюдаемость (решение A-01/A-06)

- **Регистр состояния выгрузки** (регистр сведений): по каждому объекту — последняя успешная граница/страница, статус, число строк, код последней ошибки, время. Позволяет продолжать с места обрыва и не перевыгружать лишнее (снимает P-08 в связке с аудитом).
- **Ретраи** с экспоненциальной паузой на каждую сетевую операцию; при исчерпании — пометка «повторить в следующем запуске», а не потеря.
- **Журнал регистрации** — единая обёртка: старт/финиш запуска (с идентификатором), событие на объект (выбрано/отправлено/ошибок), тело ответа ClickHouse при ошибке (усечённо), уровни. `Сообщить` — только для интерактивной отладки.
- **Метрики** — время и объёмы по таблицам для отслеживания деградации.
- **Защита от параллельного запуска** (A-02) — управляемая блокировка/флаг «идёт выгрузка».

## Рефакторинг кода (решение A-03/A-04/A-05)

- Свести три ветки и три процедуры `Выгрузка_День_*` к одной обобщённой, параметризованной типом и списком.
- Один хелпер «запрос → потоковый JSON пачки».
- **Списки метаданных и параметры** (размер пачки, окно, вкл/выкл, приоритет, префикс БД) — вынести в **регистр настроек**, управляемый без релиза.
- Магические константы — в именованные настройки; даты — через функции периодов, а не арифметику секунд.
- Секреты — в защищённое хранилище (S-01).
- DDL ClickHouse и контракт типов — в репозиторий (A-08); тесты чистых функций + dry-run (A-09).

## Поэтапный план внедрения

Порядок — по убыванию риска/выгоды. Каждый этап самостоятелен и оставляет систему работоспособной.

### Фаза 0 — Безопасность и «стоп-кран» (в течение 1–2 дней)
- 🔴 Сменить пароль `mega_user` (текущий скомпрометирован).
- 🔴 Закрыть порт 58123 файрволом, доступ только с сервера 1С.
- 🟠 Задать таймаут HTTP-соединения в `ОтправитьHTTP`.
- 🟠 Обернуть каждую сетевую операцию в `Попытка/Исключение` с логированием (чтобы один сбой не ронял весь прогон — CH-05).
- 🟡 Убрать запись в `C:\temp` (S-05).

*Результат:* прекращается утечка и «падение всего задания от одного чиха»; данные пока грузятся по-старому.

### Фаза 1 — Надёжность без смены схемы (неделя 1)
- Ретраи с паузами вокруг вставок/удалений; сбойные пачки — в «повторить», не терять.
- Отказ от `async_insert` (`= 0`) — убрать «кэш» (CH-02).
- Полное журналирование в журнал регистрации, включая тело ответа CH и ошибки вставки (A-06).
- Защита от параллельного запуска (A-02).
- Исправить K-07 (`0`/`Ложь`/`""` не терять) и K-06 (ссылки на планы счетов/ПВХ и др.).

*Результат:* заметно меньше потерь и «зависаний»; проблема мутаций и памяти ещё есть.

### Фаза 2 — Схема без мутаций (недели 2–3)
- Развернуть таблицы `ReplacingMergeTree(_version, _is_deleted)` (миграция DDL в репозитории).
- Перевести загрузку на версионный INSERT, **убрать `ALTER … DELETE`** из регулярного цикла (CH-01, K-01, K-02, K-03).
- Представления с `FINAL`/`argMax` для аналитиков; переключить потребителей на них.
- soft-delete для удалённых объектов (K-08).
- Ключи — UUID (CH-10, K-09).

*Результат:* ClickHouse перестаёт вставать; регулярная работа — только вставки; идемпотентность и самозалечивание.

### Фаза 3 — Память и масштаб (недели 3–4)
- Пагинация выборок: регистры — страницами по регистраторам (P-01, K-04); документы/справочники — обработка пачки с освобождением памяти.
- Потоковая сборка JSON (P-04); кэш имён колонок и таблицы транслитерации (P-03).
- Дробление на фоновые задания по объекту/под-периоду.
- Явные списки полей вместо `ВЫБРАТЬ *` (P-05, CH-06); временные таблицы ключей (P-06).

*Результат:* один серверный вызов не выходит за память; большие объёмы грузятся устойчиво.

### Фаза 4 — Сопровождаемость (далее)
- Рефакторинг дублей в обобщённые процедуры (A-03).
- Настройки выгрузки в данных (A-04, A-05).
- Регистр состояния и метрики (A-01); отделить свежий инкремент от «доедания» правок через аудит (P-08).
- Тесты чистых функций и dry-run (A-09); зафиксировать зависимость `Сервисный` и DDL (A-08).

## Чек-лист приёмки «надёжно»

Считаем цель достигнутой, когда:

- [ ] Регулярная выгрузка **не выполняет ни одной мутации** `ALTER … DELETE` (проверка по `system.mutations` — нет новых записей от загрузки).
- [ ] Число активных кусков стабильно, ошибок `TOO_MANY_PARTS` нет под штатной нагрузкой.
- [ ] `async_insert` выключен; вставки синхронные, результат каждой пачки детерминирован.
- [ ] Сетевой сбой/недоступность ClickHouse **не роняет** прогон: сбойные пачки помечаются к повтору и долечиваются на следующем запуске; повтор не создаёт дублей и дыр.
- [ ] Один серверный вызов 1С ограничен по памяти размером пачки; большие объёмы разбиты на фоновые задания и проходят без превышения памяти.
- [ ] Значения `0`/`Ложь`/`""` не теряются; ссылки всех типов сериализуются; даты и таймзоны согласованы с типами колонок.
- [ ] Перепроведение документа задним числом корректно отражается в регистрах (ничего не теряется — K-01/K-04).
- [ ] Секреты не в коде и не в git; обмен по HTTPS; порт закрыт от внешнего мира.
- [ ] Все значимые события и ошибки — в журнале регистрации; есть метрики по таблицам.
- [ ] Есть защита от параллельного запуска.

## Кратко

Два симптома заказчика — это две стороны «слишком много за один заход»: память серверного вызова 1С (полная материализация периода) и приём ClickHouse (шторм мутаций + async-буфер). Оба лечатся сменой модели: **регулярная работа — только идемпотентный `INSERT` в `ReplacingMergeTree`, а выборка и отправка — строго пачками с ретраями и учётом состояния**. Это даёт именно то, что просили: не обязательно быстро, но надёжно и предсказуемо, с автоматическим долечиванием сбоев.
