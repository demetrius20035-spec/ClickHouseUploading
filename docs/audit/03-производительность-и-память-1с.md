# Производительность и память на стороне 1С

Этот раздел напрямую отвечает на первый симптом заказчика: **«превышен безопасный расход памяти за один серверный вызов»** при выгрузке больших объёмов. Причина системная — данные периода целиком загружаются в память, а параметр `РазмерПачки` управляет только отправкой, но не выборкой.

Серьёзность: 🔴 Критично · 🟠 Высокий · 🟡 Средний · ⚪ Низкий

---

## 🔴 P-01. Полная материализация периода в память — прямая причина «превышен расход памяти»

**Где:**
- Регистры: `КХ_ПолучитьДанныеРегистровИзБазы_АУ` (строки 636–686) — `ВЫБРАТЬ * … Период МЕЖДУ …`, затем `Результат.Выгрузить()` и построение массива структур на **все** строки периода.
- Документы/справочники: `КХ_ПолучитьСсылкиИзБазы_АУ` (строки 471–535) выбирает **все** ссылки периода в память; далее `КХ_ПолучитьДанныеСправочниковИДокументовИзБазы_АУ` по пачке ссылок снова `Выгрузить()` в массив структур.

**Механизм превышения памяти.** Один серверный вызов (регламентное задание — это один вызов на сервере 1С) держит одновременно:

1. результат запроса `Результат` целиком;
2. его выгрузку `Выгрузка` (таблица значений на все строки);
3. `МассивСтруктур` — по структуре на каждую строку и по строковому значению на каждое поле;
4. далее ещё и `МассивПачек` из `РазбитьМассив` — **копию** всех элементов, разложенную по пачкам (см. P-02);
5. плюс собранные JSON-строки.

Для регистров `РазмерПачки` вообще не участвует в выборке (запрос тянет весь период сразу) — он применяется только к нарезке уже загруженного массива в `РазбитьМассив` (строка 179). То есть «пачки» существуют лишь на этапе HTTP-отправки, а пиковая память определяется полным объёмом периода. На активном регистре (продажи, партии, взаиморасчёты) за 7 дней это легко сотни тысяч — миллионы строк. Отсюда и падение по памяти серверного вызова.

**Как правильно (принцип).** Пагинация должна начинаться на выборке, а не на отправке:
- регистры — выбирать порциями (по регистраторам-страницам или по ключу с `ПЕРВЫЕ N` и курсором), никогда не материализуя весь период;
- документы/справочники — уже режутся на пачки ссылок, но саму выборку ссылок тоже стоит ограничивать (см. P-06) и обрабатывать пачка за пачкой, освобождая память.

Подробные эскизы — в [целевой архитектуре](06-целевая-архитектура-и-план.md), раздел «Пагинация и память».

## 🟠 P-02. Тройное представление данных в памяти + структура на каждую строку

**Где:** во всех функциях выборки; `РазбитьМассив` (строки 907–940).

**Суть.** На пути «база → JSON» данные существуют в памяти в нескольких формах одновременно:
1. `Выгрузка` — таблица значений;
2. `МассивСтруктур` — по объекту-структуре на строку (это дороже таблицы значений: каждая структура и каждый ключ — отдельные объекты);
3. `МассивПачек` из `РазбитьМассив` — **ещё одна полная копия** всех элементов, потому что функция создаёт новые вложенные массивы и копирует ссылки на все элементы (строки 930–935);
4. JSON-строки.

`РазбитьМассив` для этого физически копирует все элементы в новые массивы вместо того, чтобы отдавать «окна» (границы) в исходный массив. Пиковая память — сумма всех этих форм.

**Как правильно.** Не строить промежуточный `МассивСтруктур` на весь объём; идти построчно из выборки сразу в потоковый JSON-писатель пачками. `РазбитьМассив` заменить итератором по индексам (без копирования) или вовсе выбирать данные уже пачками.

## 🟠 P-03. Транслитерация имён выполняется на каждое поле каждой строки

**Где:** в каждой функции выборки вызов `КХ_ТранслитерироватьСтроку(ИмяКолонки)` стоит **внутри двойного цикла** (строки 519, 571, 618, 669), а сама функция (`КХ_ТранслитерироватьСтроку`, строки 737–861) на каждый вызов:
- заново создаёт `Соответствие` из 33 элементов кириллицы (строки 740–773);
- посимвольно проходит имя дважды (транслитерация, затем CamelCase→snake_case);
- прогоняет цикл удаления повторных `__`.

**Стоимость.** Имена колонок в пределах одной метаданной **постоянны**. При N строк и M колонок функция вызывается N×M раз, хотя различных имён всего M. Для 100 000 строк и 30 колонок — 3 000 000 вызовов, каждый с пересозданием словаря на 33 записи и посимвольным разбором. Это заметная доля CPU серверного вызова и лишнее давление на сборщик мусора.

**Как правильно.**
- Таблицу транслитерации создавать один раз (вынести из функции; в 1С — например, в кэш/модульную переменную или собрать один раз на процедуру).
- Имена колонок транслитерировать **один раз на метаданное** (построить соответствие «имя колонки → snake_case» перед циклом по строкам) и переиспользовать.

## 🟠 P-04. Сборка JSON конкатенацией строк в цикле — квадратичная сложность

**Где:** `КХ_СформироватьJSON` (строки 701–718):
```
СтрокаРезультат = СтрокаРезультат + Запись.Закрыть() + Символы.ПС;   // строка 714
```

**Суть.** На каждой итерации к растущей строке-результату прибавляется очередной объект. В 1С строки неизменяемы, поэтому каждая конкатенация создаёт **новую** строку длиной со всё накопленное. Для N строк это классическая сложность O(N²) по времени и всплеск памяти (постоянные пересоздания больших строк). На пачке 5000 это терпимо, но при попытке увеличить пачку деградация нелинейна.

Дополнительно: `Запись = Новый ЗаписьJSON` создаётся один раз, но `УстановитьСтроку()` / `Закрыть()` вызываются на каждый объект — то есть writer используется в режиме «строка на объект», а склейка делается вручную.

**Как правильно.** Накапливать фрагменты в `Массив` и один раз склеить `СтрСоединить(Массив, Символы.ПС)`, либо писать все объекты одним `ЗаписьJSON` в единый поток. Ещё лучше — писать JSON пачки сразу в поток/буфер отправки, не собирая гигантскую строку.

## 🟡 P-05. `ВЫБРАТЬ *` тянет вложенные табличные части и лишние поля

**Где:** `КХ_ПолучитьДанныеСправочниковИДокументовИзБазы_АУ` (строка 552) и `КХ_ПолучитьДанныеРегистровИзБазы_АУ` (строка 651): `ВЫБРАТЬ *`.

**Суть.**
- `ВЫБРАТЬ *` из справочника/документа возвращает и колонки-табличные части (тип «ТаблицаЗначений»). Их приходится отфильтровывать в коде (строка 566, см. K-14), но платформа всё равно материализует их в выгрузке — лишняя память и время. При этом ТЧ всё равно выбираются повторно отдельными запросами (строки 244, 312) — двойная работа.
- `ВЫБРАТЬ *` выгружает все реквизиты, включая ненужные аналитике (служебные, версионные), увеличивая объём в разы.
- Порядок и состав колонок при `*` не контролируются — любое изменение конфигурации меняет форму данных (связано с CH-06).

**Как правильно.** Перечислять явный список нужных реквизитов; табличные части не тянуть в основной выборке (они и так грузятся отдельно). Это уменьшит и память, и трафик, и стабилизирует схему.

## 🟡 P-06. `Ссылка В (&МассивСсылок)` на 5000 элементов вместо временной таблицы

**Где:** `КХ_ПолучитьДанныеСправочниковИДокументовИзБазы_АУ` (строки 552–553) и `КХ_ПолучитьДанныеТЧИзБазы` (строки 602–603).

**Суть.** Параметр-массив на 5000 ссылок в условии `В (&МассивСсылок)` заставляет платформу/СУБД строить большой список значений в `IN`. Для 5000 это часто приемлемо, но на грани: план запроса может деградировать, а на некоторых СУБД велик риск упереться в лимиты. Для повторяющихся выборок (шапка + каждая ТЧ по тем же ссылкам) список передаётся заново каждый раз.

**Как правильно.** Помещать пачку ссылок во временную таблицу (`ПОМЕСТИТЬ`) и соединять с ней — это стабильнее по плану и позволяет один раз материализовать набор ссылок для шапки и всех ТЧ.

## 🟡 P-07. Табличные части пачки выбираются без ограничения объёма

**Где:** `КХ_ПолучитьДанныеТЧИзБазы` (строки 590–633), вызывается для каждой ТЧ каждой пачки (строки 244, 312).

**Суть.** Пачка = 5000 ссылок документов. У «тяжёлого» документа (реализация, поступление) табличная часть может содержать десятки строк на документ. 5000 документов × десятки строк = сотни тысяч строк ТЧ в память одним запросом — и так на **каждую** табличную часть. То есть заявленная «пачка 5000» на уровне шапок превращается в существенно больший объём на уровне ТЧ, что усугубляет P-01.

**Как правильно.** Размер пачки задавать с учётом «веса» объекта (для документов с большими ТЧ — меньше); либо выбирать ТЧ тоже страницами; оценивать пиковую строку «шапка + все ТЧ пачки».

## 🟡 P-08. Семикратная перевыгрузка одних и тех же данных

**Где:** окно по умолчанию — последние 7 дней (строки 10, 28, 46), а задания суточные (имена `Выгрузка_День_*`).

**Суть.** Каждый суточный запуск заново выбирает, удаляет и вставляет данные за **7 дней**. Один и тот же день выгружается ~7 раз за неделю. Это семикратный расход: выборки из 1С (память/CPU), мутации удаления в ClickHouse (см. CH-01 — особенно вредно), трафик и вставки. Окно в 7 дней, вероятно, задумано как «защита от опоздавших правок», но реализовано самым дорогим способом.

**Как правильно.** Отделить «свежий» инкремент (за прошедшие сутки) от «доедания» правок задним числом (через аудиторский след — он и так фиксирует изменённые объекты, независимо от их даты). Тогда ежедневно обрабатывается только реально изменённое, а не весь скользящий недельный хвост.

## ⚪ P-09. Новое HTTP-соединение на каждый запрос

**Где:** `ОтправитьHTTP` (строка 723) создаёт `Новый HTTPСоединение` при каждом вызове; вызывается на каждое удаление и каждую вставку (то есть 2× на пачку, плюс по 2× на каждую ТЧ).

**Суть.** Установка соединения (а с TLS — ещё и рукопожатие) на каждый мелкий запрос добавляет задержку и накладные расходы. При сотнях пачек и десятках таблиц это тысячи установок соединения за запуск.

**Как правильно.** Переиспользовать соединение (keep-alive) в пределах обработки таблицы/задания; открывать один раз и слать несколько запросов.

## ⚪ P-10. Запрос к аудиторскому следу: неявные соединения и отсутствие явной индексации

**Где:** `КХ_ПолучитьСсылкиИзБазы_АУ`, текст запроса (строки 471–498).

**Суть.**
- Условие `АудиторскийСлед.Объект.Ссылка ЕСТЬ НЕ NULL` (строка 477) порождает неявное соединение через точку (dot-walking) с таблицей объекта — на больших объёмах аудита это дорого.
- `АудиторскийСлед.Объект ССЫЛКА Тип` (строка 476) — фильтр по типу составного поля, тоже недёшев.
- Вторая часть объединения сканирует всю таблицу справочника/документа по `ДатаСоздания` (строки 484–489) — эффективно только при наличии индекса по `ДатаСоздания` (обычный реквизит по умолчанию не индексирован).

**Как правильно.** Проверять заполненность через поле самого регистра/следа без dot-walk, где возможно; убедиться в индексируемости `ДатаСоздания` (или отбирать только через аудиторский след). Замерить план на реальных объёмах.
