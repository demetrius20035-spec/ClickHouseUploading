# Безопасность

Самая тяжёлая категория аудита. Модуль передаёт бизнес-данные предприятия во внешнюю систему по незащищённому каналу, а доступ к этой системе (логин, пароль, адрес) хранит открытым текстом в коде, который лежит в git.

Серьёзность: 🔴 Критично · 🟠 Высокий · 🟡 Средний · ⚪ Низкий

---

## 🔴 S-01. Учётные данные и адрес ClickHouse захардкожены и попали в git

**Где:** `КХ_ПолучитьДанныеАвторизации` (строки 959–967) и `КХ_ПолучитьХостПорт` (строки 969–977).

```
тСтруктура.Вставить("Пользователь", "mega_user");
тСтруктура.Вставить("Пароль", "b%250iLy8hsOf9");   // строка 964
...
тСтруктура.Вставить("Host", "5.182.6.79");          // строка 973
тСтруктура.Вставить("Port", 58123);
```

**Почему критично.**
- Логин, пароль и адрес боевого сервера ClickHouse лежат открытым текстом. Любой, у кого есть доступ к репозиторию (или к выгрузке конфигурации 1С), получает полный доступ к аналитической базе.
- Пароль уже в истории git (коммит `7e343dd`). Даже если его сейчас убрать из файла, он останется в истории — **пароль нужно считать скомпрометированным**.
- Значение `b%250iLy8hsOf9` содержит `%25` — вероятно, это уже URL-кодированный пароль (`%` → `%25`). Значит, реальный пароль, скорее всего, `b%0iLy8hsOf9`, и он «закодирован» под конкретный способ вставки в URL (см. S-03). Это отдельный признак того, что пароль руками вписан в код под транспорт.

**Что сделать (в порядке срочности):**
1. **Немедленно сменить пароль `mega_user`** в ClickHouse — текущий скомпрометирован фактом коммита.
2. Вынести секреты из кода: в 1С — в защищённое хранилище (константа с ограничением прав, параметры сеанса, или отдельное защищённое хранилище учётных данных; в идеале менеджер секретов вне 1С).
3. Убрать из истории git (переписать историю или, если проще, считать репозиторий скомпрометированным и пересоздать с чистой историей). Добавить пароли/хосты в исключения.
4. Ввести разные учётные данные для разных сред (тест/бой).

## 🔴 S-02. Обмен идёт по открытому HTTP на публичный IP

**Где:** `ОтправитьHTTP` (строки 721–734) — `Новый HTTPСоединение(Хост, Порт, , , , , Неопределено)` без защищённого соединения; TLS не используется.

**Почему критично.**
- Хост `5.182.6.79` — публичный IP, порт `58123` — нестандартный HTTP-порт ClickHouse. Весь трафик (бизнес-данные предприятия: контрагенты, договоры, суммы, движения денежных средств) идёт **в открытом виде через интернет**.
- В том же незашифрованном канале уходят **логин и пароль** (см. S-03) — их видит любой на пути пакета (провайдер, транзитные узлы, злоумышленник в сети).
- Это данные бухгалтерского и управленческого учёта — их утечка может иметь юридические и коммерческие последствия.

**Что сделать.**
- Перевести ClickHouse на HTTPS (порт 8443) с валидным сертификатом и использовать защищённое соединение в 1С (`ЗащищённоеСоединениеOpenSSL`).
- Публичный порт ClickHouse закрыть файрволом; доступ — только с адресов сервера 1С (белый список) либо через VPN/приватную сеть.
- Никогда не публиковать интерфейс ClickHouse в интернет без TLS и ограничения по IP.

## 🟠 S-03. Логин и пароль передаются в строке URL

**Где:** `КХ_УдалитьДанные` (строка 388) и `КХ_ОтправитьДанные` (строка 415):
```
Путь = "/?user=" + Пользователь + "&password=" + Пароль;                    // удаление
Путь = "/?query=" + ЗакодированныйЗапрос + "&user=" + Пользователь + "&password=" + Пароль;  // вставка
```

**Почему плохо.**
- Учётные данные в URL логируются везде: журналы прокси, журналы самого ClickHouse (`system.query_log`), журналы сетевого оборудования, отладочные трассировки 1С. Пароль расходится по логам, которые обычно защищены слабее базы.
- Пароль не проходит через URL-кодирование (`КХ_ЗакодироватьURL` применяется только к тексту запроса, строка 409). Спецсимвол в пароле сломает разбор query-string. Именно поэтому пароль пришлось «предзакодировать» руками (см. S-01) — хрупкое и опасное решение.

**Что сделать.**
- Передавать учётные данные HTTP-заголовками ClickHouse (`X-ClickHouse-User` / `X-ClickHouse-Key`) вместо query-параметров, либо стандартной Basic-аутентификацией по HTTPS.
- Не хранить «предзакодированные» пароли; кодировать при передаче, а хранить в чистом виде в защищённом хранилище.

## 🟠 S-04. SQL строится конкатенацией; экранирование неполно

**Где:** `КХ_УдалитьДанные` (строки 380–382) — список ссылок вставляется в `DELETE … WHERE … IN (...)`; имена таблиц собираются из имени метаданного (строки 185–187, 219, 240, 281, 308). Все текстовые запросы 1С тоже строятся конкатенацией имён метаданных (строки 471–498, 552, 602, 651).

**Разбор рисков.**
- В `КХ_УдалитьДанные` одинарные кавычки в ссылке экранируются (`СтрЗаменить(Ссылка, "'", "''")`, строка 368) — это единственное экранирование во всём модуле. Но значения ссылок сюда приходят из `ПолучитьНавигационнуюСсылку`/представления объекта, то есть косвенно из пользовательских данных (наименования, входящие в представление). Экранирование только одинарной кавычки — узкая защита; при смене формата поля (см. K-09) или появлении иных спецсимволов защита неполна.
- Имена таблиц и метаданных в SQL не параметризуются (в 1С это в принципе невозможно для имён), но здесь они формируются из имён объектов конфигурации и транслитерации — источник контролируемый, поэтому риск инъекции низкий; однако сам стиль «строим SQL строками» опасен и должен быть минимизирован.

**Что сделать.**
- Передавать список удаляемых ключей не инлайном в SQL, а через параметризованный механизм ClickHouse (внешние данные запроса / временная таблица / `IN` по подзапросу к загруженным ключам), избегая ручной сборки больших `IN (...)`. Это снимает и S-04, и CH-04 (превышение размера запроса).
- Значения — только как UUID (см. K-09), где спецсимволы невозможны.

## 🟡 S-05. Дамп бизнес-данных в `C:\temp` с проглатыванием ошибки

**Где:** обработка сбоя вставки документов (строки 297–303).
```
Файл = Новый ЗаписьТекста("C:\temp\Выгрузка Кликхаус.json", КодировкаТекста.UTF8);
Файл.ЗаписатьСтроку(СтрокаJSONДанные);
Файл.Закрыть();
```

**Почему плохо.**
- На диск сервера 1С в предсказуемый путь пишутся сырые бизнес-данные (JSON пачки документов) без ограничения доступа, ротации и очистки. Это неконтролируемая копия конфиденциальных данных.
- Путь жёстко задан под Windows (`C:\temp`) — на Linux-сервере 1С запись не выполнится; исключение проглатывается (`Исключение // игнорируем`), поэтому сбой даже не будет замечен.
- Это не механизм восстановления: файл перезаписывается каждой следующей сбойной пачкой и никем не читается автоматически (см. K-02).

**Что сделать.**
- Убрать запись в `C:\temp`. Для диагностики сбоев использовать журнал регистрации 1С (с усечением тела) или защищённое временное хранилище с ограничением прав и автоочисткой.
- Не проглатывать исключения молча — фиксировать факт и причину.

## 🟡 S-06. Права, квоты и сетевой доступ пользователя ClickHouse не ограничены (вне кода, но критично для контура)

**Наблюдение по коду.** Пользователь `mega_user` выполняет и `INSERT`, и `ALTER TABLE … DELETE` (мутации) — то есть обладает правами на изменение структуры/данных. Модель «один всемогущий пользователь, чьи данные лежат в git» опасна.

**Что проверить и сделать на стороне ClickHouse (DDL/конфиг вне репозитория):**
- Ограничить пользователя загрузки только нужными правами (`INSERT`, при версионной схеме — без `ALTER`/мутаций; см. [целевую архитектуру](06-целевая-архитектура-и-план.md)).
- Ограничить сетевой доступ пользователя (`<networks>` — только IP сервера 1С).
- Настроить квоты и `max_execution_time`, `max_memory_usage`, лимиты на мутации.
- Хранить учётку загрузки отдельно от учёток чтения аналитиками.

## ⚪ S-07. Самодельное URL-кодирование неполно и хрупко

**Где:** `КХ_ЗакодироватьURL` (строки 430–452).

**Суть.** Кодируется фиксированный набор ASCII-символов. Не обрабатываются:
- символы за пределами списка и не-ASCII (кириллица в тексте запроса — например, если имя таблицы/поля окажется нелатинским; в текущем коде имена транслитерируются, но текст запроса содержит и другие фрагменты);
- перевод строки, табуляция и прочие управляющие символы.

Так как через эту функцию проходит текст SQL-запроса, недокодированный символ может исказить запрос или привести к ошибке 400 от ClickHouse.

**Что сделать.** Использовать штатное кодирование платформы (`КодироватьСтроку(..., СпособКодированияСтроки.URLВКодировкеURL)`) вместо ручного списка замен; ещё лучше — передавать запрос телом/через параметры, минимизируя кодирование.
