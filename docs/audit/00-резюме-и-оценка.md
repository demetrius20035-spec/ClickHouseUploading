# Аудит модуля «ВыгрузкаКликхаус» — резюме и оценка

- **Объект аудита:** `ВыгрузкаКликхаус.bsl` (общий модуль 1С, 980 строк, коммит `7e343dd`)
- **Назначение:** выгрузка документов, справочников и регистров накопления/сведений из 1С в ClickHouse по HTTP (формат JSONEachRow), инкремент по справочнику «АудиторскийСлед» и реквизиту «ДатаСоздания»
- **Дата аудита:** 25.08.2026. Аудит выполнен в два прохода: первичный и независимый контрольный — итоги контрольного в [07-повторный-аудит-и-поправки.md](07-повторный-аудит-и-поправки.md)
- **Известные симптомы из эксплуатации:**
  1. «Превышен безопасный расход памяти за один серверный вызов» при выгрузке больших объёмов из 1С.
  2. ClickHouse: «данные сначала попадают в кэш, потом в базу; кэш быстро забивался и переставал принимать данные».
- **Целевое требование заказчика:** выгрузка должна быть **надёжной**, скорость вторична.

Оба симптома полностью объясняются кодом модуля — см. находки **P-01** (память) и **CH-01/CH-02** («кэш» = буфер асинхронных вставок + шторм мутаций `ALTER TABLE … DELETE`).

---

## Общий вердикт

**Оценка: 3 из 10.** Это работающий прототип, который решает задачу «на малых объёмах в хорошую погоду», но он **не пригоден для промышленной эксплуатации без переработки**: секреты в коде, незашифрованный канал в интернет, неатомарная схема «удалить → вставить», отсутствие ретраев и учёта состояния, загрузка всего периода в память одним вызовом, мутационная нагрузка на ClickHouse, тихие потери и искажения данных.

**Контрольный проход подтвердил вердикт**: все находки первого прохода подтверждены по коду, добавлено 10 новых находок (N-01…N-10, в том числе критичная N-01 — потеря вида движения балансовых регистров) и 5 поправок к самому отчёту (Ф-01…Ф-05, включая существенную поправку целевой архитектуры в [06](06-целевая-архитектура-и-план.md)) — подробно в [07](07-повторный-аудит-и-поправки.md).

| Категория | Оценка | Главные причины |
|---|---|---|
| Безопасность | 1/10 | Логин/пароль/IP ClickHouse захардкожены и лежат в git; открытый HTTP на публичный IP; пароль в URL; дамп данных в `C:\temp` |
| Надёжность / устойчивость к сбоям | 2/10 | DELETE→INSERT неатомарен; сетевые исключения не перехватываются и роняют всё задание; ретраев нет; сбойные пачки только считаются, но не переотправляются; таймаутов нет; простой дольше окна = невосполнимая потеря инкремента (N-05) |
| Корректность данных | 3/10 | Вид движения (приход/расход) балансовых регистров выгружается как NULL (N-01); потеря движений при перепроведении задним числом; дубли по независимым регистрам сведений; `0/Ложь/""` превращаются в NULL; ссылки на планы счетов/ПВХ теряются; удалённые объекты остаются в CH навсегда |

## Что сделано хорошо

Чтобы аудит был честным — сильные стороны, которые стоит сохранить при переработке:

- **Инкремент через «АудиторскийСлед» + «ДатаСоздания»** — правильная идея отбора изменённых объектов (для справочников и документов).
- **Батчирование по 5000** — верное направление, хотя реализовано только на этапе отправки, а не выборки.
- **JSONEachRow** — правильный формат загрузки в ClickHouse.
- **Транслитерация имён** продумана: snake_case, защита от цифры в начале, от пустого результата, от повторных `_`.
- **Централизованное преобразование типов** (`КХ_ПреобразоватьЗначение`) — единая точка, которую легко чинить.
- Ошибки хотя бы считаются и частично пишутся в журнал регистрации — есть база для нормального мониторинга.

## Топ-8 рисков (кратко)

1. **S-01/S-02 (Критично).** Учётные данные ClickHouse и адрес сервера лежат открытым текстом в git; обмен идёт по HTTP без TLS на публичный IP. Пароль скомпрометирован самим фактом коммита — **ротация обязательна немедленно**.
2. **CH-01 (Критично).** На каждую пачку каждой таблицы выполняется мутация `ALTER TABLE … DELETE` — десятки/сотни мутаций в день. Мутации переписывают куски таблиц, фоновые слияния отстают, число активных кусков растёт, и ClickHouse сначала тормозит, потом отказывается принимать вставки. Вместе с CH-02 это и есть наблюдаемое «кэш забился и перестал принимать данные».
3. **P-01 (Критично).** Регистры выгружаются запросом «всё за период» с полной материализацией в память (`Выгрузить()` + массив структур + JSON), параметр `РазмерПачки` в выборке не участвует. Это причина «превышен расход памяти за один серверный вызов».
4. **N-01 (Критично, найдено контрольным проходом).** Вид движения (приход/расход) балансовых регистров накопления выгружается как NULL: системные перечисления не обрабатываются в `КХ_ПреобразоватьЗначение`. Суммы по остаткам/партиям/взаиморасчётам в ClickHouse принципиально некорректны — требуется немедленная сверка фактических данных.
5. **K-01 (Критично).** Для регистров удаление из CH идёт по полю `registrator`, а вставка — по окну `Период`. Если у регистратора есть движения вне окна (перепроведение задним числом, изменение даты) — они **безвозвратно стираются** из ClickHouse.
6. **K-02 (Критично).** Схема «удалить → вставить» неатомарна: сбой вставки после успешного удаления оставляет дыру в данных. Ретраев нет; дыра самозалечивается только если объект снова попадёт в 7-дневное окно.
7. **CH-05 (Высокий).** `ОтправитьДляОбработки` не обёрнут в `Попытка` — любой сетевой сбой (недоступен хост, обрыв, таймаут) роняет всё регламентное задание целиком, остальные объекты не выгружаются.
8. **K-07 (Высокий).** Из-за фильтра `ЗначениеЗаполнено()` значения `0`, `Ложь` и пустые строки превращаются в `NULL` — суммы и флаги в ClickHouse искажаются.
