### Ф-02. Несогласованная серьёзность K-14

В `01-ошибки-корректности.md` заголовок K-14 (сравнение `ОписаниеТипов` через `=`) помечен 🟡, а в итоговых таблицах (и в карте `00`) — ⚪. ### Ф-03. Существенная поправка целевой архитектуры: `FINAL` недостаточен для ТЧ и регистров («фантомные строки»)

Первая редакция `06` предлагала читать все таблицы через представления с `FINAL`. Это **корректно только для шапок** (ключ сортировки = `uuid`, одна строка на объект). Для табличных частей (ключ `(uuid, nomer_stroki)`) и регистров (ключ `(registrator, period, nomer_stroki)`) `FINAL` дедуплицирует лишь строки **с совпадающим ключом**. Если в новой версии документа строк стало меньше (было 10, стало 8) или движение сменило `period` при перепроведении, у строк старой версии **нет пары с тем же ключом** — они не схлопнутся и останутся видимыми («фантомы»), в том числе через `FINAL`.

Без этой поправки версионная схема воспроизводила бы K-01/K-03 в новой форме — лишние строки вместо потерянных.

**Исправление (внесено в `06`):**
- представления для ТЧ и регистров фильтруют по **последней версии владельца** (`max(_version)` по шапке / по регистратору), а `FINAL` остаётся только для гашения дублей от повторов одной версии;
- порядок вставки внутри пачки — **сначала все ТЧ, последней шапка**: шапка играет роль «коммита» версии, частичный сбой не виден читателям;
- пачка регистров режется **строго по границам регистраторов** (все движения регистратора — в одном INSERT), чтобы версия была атомарна на регистратора;
- фантомы физически чистятся редкой плановой зачисткой вне пиков (единственная допустимая мутация в целевой схеме);
- уточнено требование версии: `ReplacingMergeTree(ver, is_deleted)` доступен с **ClickHouse 23.2**; на более старых версиях — `ReplacingMergeTree(_version)` и фильтр `_is_deleted` в представлении.

### Ф-04. Дополнения к списку мёртвого кода (к K-17)

### Ф-05. Уточнение к CH-02 (механика async-буфера)

Вывод CH-02 (отключить `async_insert` для пачечной загрузки) не меняется — он только усиливается.

## Часть 2. Новые находки (N-01…N-10)

### 🔴 N-01. Вид движения регистров накопления выгружается как NULL — приход и расход неразличимы

**Где:** `КХ_ПреобразоватьЗначение` (строки 864–904) в связке с `ВЫБРАТЬ *` по регистрам (строка 651) и фильтром `ЗначениеЗаполнено` (строки 671–675).

**Механика.** У регистров накопления вида «остатки» выборка `ВЫБРАТЬ *` возвращает колонку `ВидДвижения` типа `ВидДвиженияНакопления` — это **системное перечисление**, а не перечисление конфигурации. Проверка на строке 867 использует `Перечисления.ТипВсеСсылки()`, которая содержит **только перечисления конфигурации** (`ПеречислениеСсылка.*`). Системное перечисление не проходит ни одну ветку функции (не справочник/документ, не число/строка/дата/УИД/булево) → функция возвращает `Неопределено` → в JSON уходит `null`.

**Последствия.** В текущем списке выгружаемых регистров большинство — балансовые: `ДенежныеСредстваБанк/Касса/ВПути/ИсточникиФинансирования`, `ОстаткиТовараНаСкладах`, `ПартииТоваровНаСкладах`, `ВзаиморасчетыС*` (строки 116–135). Для всех их строк поле `vid_dvizheniya`:
- либо приходит `null` и превращается в дефолт колонки — **приход и расход неотличимы**, любые агрегаты (остатки, обороты со знаком) в ClickHouse принципиально некорректны;
- либо (если колонки в таблице CH нет и включена строгая проверка полей) **ломает вставку всей пачки**.

Ошибка тихая: HTTP 200, счётчики «загружено», журнал пуст. Это худший класс дефекта для аналитической системы.

**Как исправить.** В `КХ_ПреобразоватьЗначение` добавить обработку системных перечислений (`Строка(тЗначение)` → «Приход»/«Расход», а лучше — числовой знак +1/−1 отдельной колонкой) и вообще заменить «ни одна ветка не совпала → `Неопределено`» на осмысленный фолбэк `Строка(тЗначение)` с журналированием незнакомого типа. Обязательно **сверить фактические данные в ClickHouse** по балансовым регистрам: если там уже NULL/пусто — данные за всю историю выгрузки требуют перезаливки после исправления.

### 🟠 N-02. Непериодический независимый регистр сведений роняет всё задание

**Где:** `КХ_ПолучитьДанныеРегистровИзБазы_АУ`, текст запроса `ГДЕ … Период МЕЖДУ …` (строка 651).

Ветка регистров синтаксически поддерживает регистры сведений (строки 168, 184–185), но запрос жёстко обращается к полю `Период`. У **непериодического** независимого регистра сведений поля `Период` нет → запрос не скомпилируется → необработанное исключение (см. CH-05) → падает всё регламентное задание, объекты после сбойного не выгружаются. Для **периодического** независимого РС запрос выполнится, но сработает K-05 (дубли из-за «успешного» удаления по отсутствующему `registrator`).

Сейчас в списках только регистры накопления, поэтому дефект спит; это мина с двумя разными взрывателями (падение либо дубли) при первом же расширении списка. Исправление — то же, что для K-05/K-10: определять состав полей по метаданным конкретного регистра и оборачивать каждый объект в `Попытка`.

### 🟡 N-03. Список DELETE по регистраторам не дедуплицирован — SQL раздувается в разы

**Где:** `КХ_УдалитьДанные`, сбор `СписокСсылок` (строки 363–372) из пачки **строк** регистра.

Для регистров структурой пачки является строка движения, и `registrator` повторяется в списке столько раз, сколько строк у документа в пачке. В `IN (...)` уходит до 5000 значений, из которых уникальных обычно сотни. Последствия: текст DELETE раздувается в разы → порог `max_query_size` (CH-04) достигается кратно раньше; парсинг и мутация обрабатывают лишние литералы. Исправление тривиально (`Соответствие` для уникальности), но в целевой схеме удалений нет вовсе — там это неактуально.

### 🟡 N-04. Даты вне диапазона ClickHouse не фильтруются

**Где:** `КХ_ПреобразоватьЗначение`, ветка дат (строки 882–895).

1С допускает даты с годом 1–3999, и ошибочные пользовательские даты (например, «0203 год» вместо «2023») в учётных базах — обычное дело. Обрабатывается только «пустая» дата `0001-01-01` (→ `null`); всё остальное уходит строкой как есть. `DateTime` в ClickHouse ограничен диапазоном 1970–2106: значение вне диапазона в зависимости от версии/настроек либо молча искажается (сатурация к границе диапазона), либо бьёт вставку пачки. Нужна валидация диапазона на стороне 1С (вне диапазона → `null` + запись в журнал) и договорённость о типах колонок (`DateTime64`/`Nullable`).

### 🟡 N-05. Простой заданий дольше окна — невосполнимая потеря инкремента

**Где:** фиксированное окно «последние 7 дней» от текущей даты (строки 10, 14, 28, 32, 46, 50) + отсутствие учёта состояния (A-01).

Окно отсчитывается от «сейчас», а не от последней успешной выгрузки. Если задания не работали дольше 7 дней (сбой инфраструктуры, отпуск администратора, забытое отключение), записи аудиторского следа за пропущенные дни навсегда выпадают из окна — изменения тех дней **никогда** не будут выгружены, и никакой сигнал об этом не появится. Это конкретный, легко воспроизводимый сценарий тихой потери, который первый проход сформулировал лишь абстрактно («нет состояния»). Исправление: границу «от» брать из регистра состояния (последний успешный период по объекту), окно — лишь верхний предел порции.

### 🟡 N-06. Неактивные движения выгружаются наравне с активными (и их флаг превращается в NULL)

**Где:** запрос по регистрам без условия по `Активность` (строка 651).

Записи регистров с `Активность = Ложь` (отключённые движения) в 1С не участвуют в итогах, но выгружаются в ClickHouse наравне с активными и попадают во все суммы. Пикантность: сам флаг `Активность = Ложь` из-за K-07 (`ЗначениеЗаполнено`) превращается в `null`, то есть в CH активные строки имеют `true`, а неактивные — `null`/дефолт: отфильтровать можно, но только зная об этой особенности, и только при `Nullable`-колонке. Исправление: либо `ГДЕ Активность` в запросе, либо честно выгружать флаг (после исправления K-07) и фильтровать в представлениях.

### ⚪ N-07. Перечисления сериализуются синонимом — нестабильные ключи аналитики

**Где:** `КХ_ПреобразоватьЗначение`, строки 867–868 (`Строка(тЗначение)` для перечислений).

`Строка()` от перечисления возвращает синоним — пользовательское представление, которое меняется при правке конфигурации и зависит от языка. Все исторические данные в CH остаются со старым текстом, новые приходят с новым → группировки расщепляются. Надёжный ключ — имя значения перечисления (`Метаданные`/`XMLСтрока`), представление — отдельным полем при необходимости.

### ⚪ N-08. Возможны коллизии имён полей после транслитерации

**Где:** `КХ_ТранслитерироватьСтроку` + `СтруктураЗаписи.Вставить` (строки 519/527, 571/579, 618/626, 669/677).

Разные имена реквизитов могут дать одно snake_case-имя (например, «СуммаНДС» и «Сумма_НДС» → `summa_nds`; «е»/«э» транслитерируются одинаково). `Структура.Вставить` при совпадении ключа молча перезаписывает значение — колонка теряется без какого-либо сигнала. Вероятность в конкретной конфигурации низкая, но проверка отсутствует в принципе; при построении карты имён (P-03) стоит добавить контроль уникальности с ошибкой на старте.

### ⚪ N-09. Неподдерживаемые типы метаданных игнорируются молча

**Где:** `КХ_Загрузить_из_ОС`, цепочка `Если … ИначеЕсли …` без ветки `Иначе` (строки 168–337).

Если в массив попадёт метаданное вне четырёх поддерживаемых видов (например, регистр бухгалтерии или расчёта), процедура не сделает ничего: ни ошибки, ни записи в журнал — только пустая статистика. Вызвавший будет считать, что выгрузка прошла. Дополнение к K-11: нужна явная ветка `Иначе` с ошибкой/журналированием.

### ⚪ N-10. Конструктивный лаг свежести данных — минимум сутки

**Где:** `ПериодДо = КонецДня(ТекущаяДатаСеанса() - 86400)` («вчера», строки 13–15, 31–33, 49–51).

Данные текущего дня не выгружаются по построению; изменение, сделанное сегодня, попадёт в ClickHouse только завтрашним запуском (а при изменении «сегодняшним днём после окна» — послезавтрашним). Для суточной управленческой аналитики это, вероятно, осознанный выбор — но он нигде не зафиксирован. Стоит либо задокументировать SLA свежести, либо снять ограничение (при версионной схеме перевыгрузка «сегодня» завтра безопасна).

## Часть 3. Что контрольный проход дополнительно подтвердил

Выборочно — самые важные верификации первого прохода (все 53 находки сверены с кодом, расхождений не найдено):

- **K-01 / K-04 (регистры).** Несовпадение предикатов подтверждено дословно: удаление — `WHERE registrator IN (…)` по регистраторам из выборки, вставка — только строки с `Период` в окне (строки 190–201 против 651). Сценарий потери januar-строк при перепроведении воспроизводится по коду однозначно.
- **P-01 (память).** `РазмерПачки` действительно не участвует ни в одном запросе; единственное упоминание в выборке регистров — мёртвая переменная `РазмерПачкиСтрокой` (Ф-04). Пиковая память = полный период × (результат запроса + таблица значений + массив структур + пачки).
- **CH-04 (размер DELETE) — подтверждён количественно.** Навигационная ссылка с кириллическим именем типа в UTF-8 — порядка 100–160 байт; 5000 значений с кавычками и запятыми — ориентировочно 0,6–0,8 МБ, что в 2–3 раза выше `max_query_size` по умолчанию (256 КБ). С учётом недедуплицированного списка (N-03) порог достигается ещё раньше. То есть удаления крупных пачек, скорее всего, **уже** падают, а поскольку при ошибке удаления вставка пропускается — данные этих пачек молча не обновляются.
- **K-07 (`0`/`Ложь`/`""` → NULL).** Семантика `ЗначениеЗаполнено` подтверждена; фильтр стоит во всех четырёх функциях выборки (строки 521, 573, 620, 671). Связка с N-01 и N-06 делает эту находку ещё весомее.
- **CH-01/CH-02 (причина «кэш забился»).** Модель «шторм мутаций → отставание слияний → рост кусков → отказ вставок; async-буфер — сопутствующий фактор» подтверждена; альтернативных объяснений в коде не обнаружено.
- **S-01.** Пароль в коде хранится в предварительно URL-кодированном виде (`%25` = закодированный `%`), что подтверждает ручную подгонку секрета под транспорт и делает ротацию обязательной.
