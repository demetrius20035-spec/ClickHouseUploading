# Ошибки корректности и потери/искажения данных

Здесь собраны дефекты, из-за которых данные в ClickHouse расходятся с 1С: теряются, дублируются, искажаются или не обновляются. Для системы аналитики это опаснее падений — падение видно, а тихое расхождение нет.

Серьёзность: 🔴 Критично · 🟠 Высокий · 🟡 Средний · ⚪ Низкий

---

## 🔴 K-01. Регистры: удаление по регистратору, вставка по периоду → безвозвратная потеря движений

**Где:** `КХ_Загрузить_из_ОС`, ветка «Регистры» (строки 171–204); `КХ_ПолучитьДанныеРегистровИзБазы_АУ` (строки 636–686); `КХ_УдалитьДанные` с `ПолеОтбора = "registrator"` (строка 190).

**Суть.** Данные регистра выбираются по окну `Период МЕЖДУ &ПериодОт И &ПериодДо` (строка 651). Затем удаление из ClickHouse выполняется по списку **регистраторов**, попавших в выборку (`DELETE WHERE registrator IN (...)`). Но удаляются **все** строки этих регистраторов, а вставляются только строки, чей `Период` попал в окно.

**Сценарий потери данных:**
1. Документ проведён 1 июня, создал движения на 1 июня и (сторно/корректировка) на 1 января.
2. Документ перепроведён в текущем окне (последние 7 дней), его регистратор попал в выборку.
3. `DELETE WHERE registrator = 'этот_документ'` удаляет из ClickHouse **и июньскую, и январскую** строки.
4. Запрос выбрал только строки с `Период` за последние 7 дней → январская строка не выбрана → в INSERT её нет.
5. **Январское движение исчезло из ClickHouse навсегда** и вернётся, только если документ снова перепроведут.

Регистры с движениями «задним числом» (взаиморасчёты, партии, остатки — а в списке `КХ_ПолучитьМассивМетаданныхОтправляемыхРегистров` именно они) страдают в первую очередь.

**Как правильно.** Единица идемпотентности должна совпадать у удаления и у вставки. Варианты: (а) удалять и вставлять строго по одному ключу — либо весь регистратор целиком (тогда и выбирать все его движения, а не окно по периоду), либо по составному ключу строки; (б) перейти на схему без удалений (ReplacingMergeTree по версии) — см. [целевую архитектуру](06-целевая-архитектура-и-план.md), где эта проблема снимается конструктивно.

## 🔴 K-02. Схема «удалить → вставить» неатомарна: сбой вставки оставляет дыру в данных

**Где:** для регистров строки 191–201; для справочников 222–237; для документов 283–305.

**Суть.** Логика всюду одинакова: сначала `КХ_УдалитьДанные` (мутация `ALTER TABLE … DELETE`), при коде 200 — `КХ_ОтправитьДанные` (INSERT). Между ними нет транзакции. Если удаление прошло, а вставка не удалась (сеть, перегрузка ClickHouse, дрейф схемы, слишком большой запрос), то:

- старые данные уже удалены;
- новые не вставлены;
- код лишь увеличивает счётчик `тОшибокЗаписи*` и делает `Продолжить` (строки 195–196, 235–236, 296–304);
- **пачка данных теперь отсутствует в ClickHouse.**

Ретрая нет. Самолечение возможно только если те же объекты снова попадут в 7-дневное окно на следующем запуске — для документов и справочников это случайность, для регистров (см. K-01/K-04) может не случиться никогда.

**Особо для документов** (строки 297–303): при сбое вставки JSON пачки пишется в `C:\temp\Выгрузка Кликхаус.json`, перезаписывая предыдущий файл, а исключение записи проглатывается. Это не механизм восстановления, а видимость его: файл переживёт лишь до следующей сбойной пачки и никем не читается.

**Как правильно.** Порядок «вставить новое → убедиться → погасить старое» плюс идемпотентность (версия выгрузки/`ReplacingMergeTree`), чтобы сбой в любой точке не создавал дыру, а лишь оставлял временный дубль, который схлопнется при слиянии. См. [целевую архитектуру](06-целевая-архитектура-и-план.md).

## 🟠 K-03. Рассинхрон шапки и табличных частей при частичных сбоях

**Где:** документы 285–325, справочники 224–258.

**Суть.** Шапка объекта и его табличные части грузятся отдельными парами DELETE+INSERT в отдельные таблицы. Точек независимого отказа много:

- шапка вставилась, ТЧ — нет (INSERT ТЧ упал, строки 315–318): в аналитике документ есть, а его строк нет — суммы «шапка vs строки» не сходятся;
- удаление ТЧ упало (строки 319–324): старые строки ТЧ остаются, при этом ветка помечена `//Продолжить` закомментированным, то есть выполнение **идёт дальше** к следующей ТЧ, не прерывая объект, — старые строки этой ТЧ так и остаются, поверх могут не лечь новые;
- у документа несколько ТЧ — часть обновилась, часть нет.

Итог — регулярно неконсистентные документы, которые невозможно надёжно отличить от корректных без внешней сверки.

**Как правильно.** Грузить объект целиком как единицу согласованности: либо все его таблицы обновились, либо ни одна не «поехала». В версионной схеме — одна версия выгрузки на шапку и все её ТЧ, чтение только консистентной версии.

## 🟠 K-04. Регистры игнорируют аудиторский след: правки задним числом не доезжают

**Где:** `КХ_ПолучитьДанныеРегистровИзБазы_АУ` (строка 651) против `КХ_ПолучитьСсылкиИзБазы_АУ` (строки 471–498).

**Суть.** Для справочников и документов изменённые объекты берутся из «АудиторскийСлед» (любое изменение за период попадёт в выборку). Для регистров отбор идёт только по `Период` самих движений. Но у регистра движение с `Период` = январь могло быть **создано/изменено вчера** (перепроведение старого документа). Такое движение никогда не попадёт в 7-дневное окно по `Период` и, значит, никогда не обновится в ClickHouse.

Вместе с K-01 это даёт двойной удар по регистрам: старое движение и не обновляется (K-04), и может быть стёрто при перепроведении (K-01).

**Как правильно.** Отбирать движения регистров по регистраторам, изменённым за период (через тот же аудиторский след / период регистратора), а не по периоду самих записей; либо вести отдельную отметку последней выгрузки на регистратор.

## 🟠 K-05. Независимые регистры сведений: «успешное» удаление без реального удаления → дубли

**Где:** `КХ_УдалитьДанные` (строки 363–376), формирование поля отбора для регистров — всегда `registrator` (строка 190).

**Суть.** Поле отбора для регистров жёстко задано как `registrator`. У **независимого регистра сведений** регистратора нет вовсе. Тогда:
- поле `registrator` в структурах отсутствует → `СписокСсылок` пуст → `КХ_УдалитьДанные` возвращает 200 (строки 374–375), **ничего не удалив**;
- дальше выполняется INSERT.

Результат — старые строки не удаляются, новые добавляются: **дубли** при каждом запуске. В текущем списке метаданных независимых регистров сведений нет (только регистры накопления с регистратором), но конструкция — мина: добавление любого независимого регистра сведений начнёт молча плодить дубли. То же произойдёт при коде удаления 200 «по пустому списку» в любой ветке (строки 374–375): вернуть «успех» без действия и вставить поверх.

**Как правильно.** Ключ удаления должен определяться измерениями конкретного регистра (для независимого РС — его измерения), а «нечего удалять» не должно молча открывать путь вставке поверх непочищенных данных.

## 🟠 K-06. Ссылки на планы счетов / ПВХ / ПВР / бизнес-процессы / задачи теряются (→ NULL)

**Где:** `КХ_ПреобразоватьЗначение` (строки 864–904).

**Суть.** Явно обрабатываются только перечисления (867), справочники и документы (869). Ссылочные значения других типов — **ПланыСчетов, ПланыВидовХарактеристик, ПланыВидовРасчёта, БизнесПроцессы, Задачи, ПланыОбмена** — не подпадают ни под одну ветку, и функция возвращает `Неопределено`. В JSON это станет `null`.

Регистры бухгалтерии/расчёта и их измерения (счёт, вид субконто, вид расчёта) при выгрузке потеряют ключевые ссылки. Ошибка тихая: код 200, данные «загружены», но аналитика по счетам пуста.

**Как правильно.** Обрабатывать все ссылочные типы обобщённо — например, через общую проверку «это ссылка» и единый способ сериализации (навигационная ссылка или UUID+представление), а не перечислять типы вручную.

## 🟠 K-07. Значения `0`, `Ложь` и пустые строки превращаются в NULL

**Где:** во всех функциях выборки перед вызовом преобразования стоит `Если ЗначениеЗаполнено(ЗначениеЯчейки) Тогда … Иначе ЗначениеПоля = Неопределено` (строки 521–525, 573–577, 620–624, 671–675).

**Суть.** `ЗначениеЗаполнено` в 1С считает «незаполненными» число `0`, `Ложь`, пустую строку, пустую дату. Все они заменяются на `Неопределено` → в JSON уходит `null` (либо поле опускается — см. ниже). Последствия:

- числовой реквизит со значением `0` (остаток, сумма, количество) → `NULL`. В аналитике `SUM`/`AVG` и разбиение на нули искажаются;
- булев реквизит `Ложь` → `NULL`, теряется различие «Ложь» и «не задано»;
- пустая строка → `NULL`.

Дополнительно: в `КХ_СформироватьJSON` (строки 705–715) для значения `Неопределено` `ЗаписатьЗначение` обычно пишет `null`, но семантика «значение было нулём» уже утрачена в момент выборки — почему поля искажаются одинаково независимо от сериализации.

**Как правильно.** Не отбрасывать «незаполненные» значения по `ЗначениеЗаполнено`. Пропускать через преобразование само значение и решать по его типу: `0` и `Ложь` — валидные данные, их надо отдавать как есть.

## 🟡 K-08. Удалённые в 1С объекты навсегда остаются в ClickHouse

**Где:** вся модель выгрузки; отбор в `КХ_ПолучитьСсылкиИзБазы_АУ` (строки 471–498).

**Суть.** Модуль умеет только «есть/обновилось». Когда объект в 1С помечен на удаление и физически удалён, он перестаёт попадать в выборки — но в ClickHouse остаётся последняя выгруженная версия навсегда. Аналитика по «живым» данным будет включать давно удалённые документы/элементы.

Пометка на удаление тоже не отражается корректно: `ВЫБРАТЬ *` вернёт реквизит `ПометкаУдаления`, но пока объект существует и попадает в окно — он выгрузится как обычная строка; после физического удаления обновление прекратится на «непомеченной» версии.

**Как правильно.** Ловить удаления (подписка на удаление объектов / отдельный журнал удалений) и отражать их в ClickHouse как soft-delete (флаг + версия), а не пытаться физически удалять.

## 🟡 K-09. Фолбэк `Строка(Ссылка)` для предопределённых ломает обратный парсинг навигационной ссылки

**Где:** `КХ_ПреобразоватьЗначение` (строка 870); обратное преобразование — `МассивСтруктурСсылокВМассивСсылок` → `Сервисный.ПолучитьСсылкуИзНавигационнойСсылки` (строки 943–953).

**Суть.** Значение ссылки обычно сериализуется навигационной ссылкой `ПолучитьНавигационнуюСсылку`. Но при исключении (например, предопределённые элементы) в поле уходит `СокрЛП(Строка(тЗначение))` — человекочитаемое представление, а не навигационная ссылка. На следующем шаге поле `ssylka` пачки документов/справочников снова превращается в ссылку через `ПолучитьСсылкуИзНавигационнойСсылки`. Для строк-представлений этот парсинг вернёт пустую/некорректную ссылку → пачка «поедет»: часть объектов не найдётся при повторной выборке данных (строка 552 `Ссылка В (&МассивСсылок)`).

Ситуация локализована полем `ssylka`, но показывает системную хрупкость: одно поле служит и данными, и ключом идемпотентности, и по нему же строится обратный парсинг.

**Как правильно.** Ключом идемпотентности сделать стабильный `UUID` ссылки (`Строка(Ссылка.УникальныйИдентификатор())`), а представление хранить отдельным полем. Тогда обратное преобразование не зависит от текстового представления.

## 🟡 K-10. Жёсткое требование реквизита «ДатаСоздания»: объект без него роняет задание

**Где:** `КХ_ПолучитьСсылкиИзБазы_АУ`, текст запроса (строки 484–489).

**Суть.** Во второй части объединения запрос обращается к `<Объект>.ДатаСоздания` для **каждого** справочника и документа из списков. Если у какого-то из объектов нет реквизита `ДатаСоздания`, запрос не скомпилируется и упадёт с исключением. Исключение не перехвачено (см. CH-05) → падает всё задание, ни один объект после сбойного не выгрузится.

То есть работоспособность модуля зависит от того, что у **всех** перечисленных метаданных есть одноимённый реквизит `ДатаСоздания` (видимо, добавленный в конфигурацию). Это неявная и хрупкая зависимость.

**Как правильно.** Проверять наличие реквизита через метаданные перед построением запроса и корректно ветвиться (или опираться только на аудиторский след); в любом случае — оборачивать обработку каждого объекта в `Попытка`.

## 🟡 K-11. Ветвление по первому элементу массива; пустой массив роняет процедуру

**Где:** `КХ_Загрузить_из_ОС`, строки 168, 207, 270 — `МассивМетаданных[0]`.

**Суть.** Тип обработки (регистр/справочник/документ) определяется по **первому** элементу массива. Из этого следует:

- если в один массив попадут разнотипные метаданные, все будут обработаны по типу первого (сейчас вызовы формируют однотипные массивы, но контракт нигде не закреплён — это ловушка на будущее);
- если массив пуст, обращение `МассивМетаданных[0]` вызовет ошибку индекса. Вызовы защищены проверкой `Количество() > 0` в регламентных процедурах (строки 18, 36, 54), но сама `КХ_Загрузить_из_ОС` экспортная и может быть вызвана напрямую — тогда упадёт.

**Как правильно.** Определять тип каждого элемента внутри цикла, а не по `[0]`; на входе проверять непустоту массива.

## 🟡 K-12. `РазбитьМассив`: недостижимая проверка и `[[]]` для пустого массива

**Где:** `РазбитьМассив` (строки 907–940).

**Суть.** Порядок проверок неверен:
```
Если тВсего < РазмерПачки Тогда  тИтогМассив.Добавить(тМассив); Возврат …  // строки 912–915
Если тВсего = 0 Тогда  Возврат тИтогМассив;                                 // строки 917–919 — недостижимо
```
При `тВсего = 0` условие `0 < РазмерПачки` истинно, поэтому функция вернёт `[ [] ]` — массив с одной пустой пачкой, а не пустой результат. Проверка на ноль ниже никогда не срабатывает (мёртвый код). На практике до `РазбитьМассив` доходят только непустые массивы (есть ранний `Продолжить` при количестве 0), поэтому баг сейчас латентный, но логика функции некорректна и вводит в заблуждение.

**Как правильно.** Сначала обрабатывать `тВсего = 0` (возврат пустого результата), затем остальные случаи; проверки в правильном порядке.

## 🟡 K-13. Эвристика «строка похожа на дату» может калечить строковые данные

**Где:** `КХ_ПреобразоватьЗначение`, строки 874–880.

**Суть.** Для значений типа «Строка» длиной ровно 19 с двумя `:` и двумя `-` код считает, что это дата, и если «время» = `00:00:00`, обрезает строку до 10 символов. Любая реальная строка такого формата (например, техническое поле, серийный код, произвольный текст пользователя, случайно совпавший по маске) будет обрезана и искажена.

**Как правильно.** Не угадывать тип по маске строки. Даты приходят типом «Дата» и обрабатываются своей веткой; строку отдавать как есть.

## 🟡 K-14. Сравнение `ОписаниеТипов` через `=` — хрупкая проверка табличной части

**Где:** `КХ_ПолучитьДанныеСправочниковИДокументовИзБазы_АУ`, строка 566: `Если Колонка.ТипЗначения = Новый ОписаниеТипов("ТаблицаЗначений")`.

**Суть.** Сравнение объектов `ОписаниеТипов` оператором `=` полагается на то, что описание типа колонки будет в точности равно вновь созданному описанию «ТаблицаЗначений». Это работает не во всех случаях (составные типы, разные экземпляры описания) и является недокументированной деталью платформы. Надёжнее проверять через `СодержитТип(Тип("ТаблицаЗначений"))`. Если проверка не сработает, табличная часть попадёт в шапку как вложенная структура и сломает JSON/вставку.

**Как правильно.** Использовать `Колонка.ТипЗначения.СодержитТип(Тип("ТаблицаЗначений"))`.

## ⚪ K-15. Счётчики «загружено N» показывают выбранное, а не доставленное

**Где:** `тСчетчик` инкрементируется до отправки (строки 177, 229, 290) и печатается независимо от результата отправки (строки 203, 266, 333).

**Суть.** Сообщение «<Объект> — загружено — N» печатает количество **выбранных** записей, а не реально записанных в ClickHouse. При сбоях вставки (которые лишь увеличивают счётчик ошибок и делают `Продолжить`) сообщение всё равно покажет полное N. Ложное ощущение успеха, маскирующее K-02.

**Как правильно.** Считать отдельно «выбрано / отправлено успешно / ошибок» и логировать все три; статус запуска выводить итогом.

---

## ⚪ K-16. `СокрЛП(УникальныйИдентификатор)` — потенциальная ошибка типа

**Где:** `КХ_ПреобразоватьЗначение`, строка 897: `тНовоеЗначение = СокрЛП(тЗначение)` для типа «УникальныйИдентификатор».

**Суть.** `СокрЛП` ожидает строку. Передача `УникальныйИдентификатор` полагается на неявное приведение; в зависимости от платформы это может дать ошибку или неожиданный результат. Корректно — `СокрЛП(Строка(тЗначение))`, как сделано для дат.

**Как правильно.** Явно приводить к строке перед `СокрЛП`.

---

## ⚪ K-17. Мёртвый код и мёртвые ветки

**Где и что:**
- Функция `ПреобразоватьЧисло` (строки 693–698) не используется (вызов закомментирован на строке 872).
- Закомментированный `//Продолжить;` (строки 256, 263, 323, 330) создаёт ложное впечатление, что ветка прерывает итерацию, тогда как выполнение продолжается — легко ошибиться при правках (связано с K-03).
- Закомментированные `//Сообщить("======СтрокаJSON …")` (строки 394, 422) — отладочные остатки.
- В `КХ_ПреобразоватьЗначение` переменная `тЗначениеДата` (строка 883) вычисляется, но не используется.
- Закомментированные альтернативные форматы дат (строки 886, 889) — накопленный «мусор» решений.

**Как правильно.** Удалить мёртвый код; закомментированные `Продолжить` либо включить, либо убрать, приведя поведение в соответствие с намерением.
